# 승인된 순수 규칙 테스트 구현 루프

진입점은 `scripts/loop.sh`, 실행 제어는 `scripts/loop.mjs`이다.
프로젝트의 Node.js 24와 설치된 Codex CLI·npm·Git을 사용한다.
이번 작업은 파일 작성과 구문 검사만 수행했다. 아래 명령은 아직 실행하지 않았다.

## 사용자 실행

프로젝트 루트에서:

```sh
scripts/loop.sh "작업 설명"
```

- 작업 설명은 따옴표로 묶은 필수 인수 1개다. 누락·빈 문자열·공백뿐인 설명·추가 인수는 기록·잠금·검사·Codex 실행 전에 거절한다. 결제 작업 기본값은 없다.
- 예: `scripts/loop.sh "T-26 일반 예약 노쇼 전이의 승인된 순수 규칙 테스트를 구현해 줘"`. 작업 설명은 매 바퀴 프롬프트와 `run.json`에 전달·기록되며, 기록의 비밀값 마스킹은 유지한다.
- 작업별 US·AC·T·C, 선행 완료와 테스트 사용자 확인 근거를 에이전트가 확인한다. 테스트 커밋이나 작업 설명만으로 승인 완료를 가정하지 않는다. 근거 누락·미확정 정책은 `BLOCKED`로 보고한다.
- 수정 범위는 `src/rules`의 순수 함수·공개 export다. 전체 규칙 테스트 검사는 유지하므로 다른 작업의 실패도 남으면 전체 통과로 종료하지 못한다. 요청 밖의 실패를 고치도록 작업 범위를 넓히지는 않는다.
- 승인한 테스트는 먼저 커밋되어 있어야 한다. 변경·미추적·무시된 미커밋 테스트가 있으면 시작하지 않는다.
- 사용자가 `.codex/TEST_WRITING`을 꺼 둬야 한다. 파일이 남아 있으면 `BLOCKED`로 기록하고 종료한다. 루프는 스위치를 만들거나 지우지 않는다.
- 테스트·훅·정책·설정·루프 자체의 변경은 중단 사유다. 변경 내용을 자동으로 되돌리지 않는다.
- 동시에 두 루프가 같은 저장소에서 실행되지 않도록 `artifacts/loops/.running` 잠금을 사용한다. 강제 종료로 남은 잠금은 사용자가 실행 중인 프로세스를 확인한 뒤 직접 정리한다.

## 한 바퀴와 제한

0. 시작 시 전체 규칙 테스트와 타입 검사로 기준 결과를 기록한다. 이미 전부 통과하면 Codex를 부르지 않고 종료한다. 실패 확인은 이 시점에 승인된 테스트로 수행한다.
1. 직전 실패 사례와 타입 오류를 전달하여 `codex exec --sandbox workspace-write --json`으로 구현 수정을 요청한다. 모델·프로필은 사용자 기본 설정을 따른다. 보호·신뢰를 우회하는 옵션은 사용하지 않는다.
2. 수정 후 전체 `npm run test:rules`를 JSON 보고서로 실행하고 `npm run typecheck`도 확인한다.
3. 동일한 테스트 파일·전체 이름별 연속 실패 횟수를 기록한다. 실제 통과한 사례만 횟수를 0으로 만든다. 미수집·skip·todo·잘못된 보고서는 횟수를 초기화하지 않고 중단한다.
4. 테스트와 타입 검사가 모두 통과하면 종료한다. 실패하면 다음 수정 바퀴로 넘어간다.

- 수정 바퀴는 최대 **5회**다. 기준 검사는 0바퀴이며 3바퀴 연속 실패 집계에는 포함하지 않는다.
- 전체 실행 시간은 기준 검사부터 **20분**이다. Codex·테스트·타입 검사 모두 같은 남은 시간을 사용하며 기한에 실행 중 프로세스 그룹을 종료한다.
- 같은 테스트가 **3바퀴 연속 실패**하면 다음 수정을 하지 않는다. 예: A 실패 → A 실패 → A 실패는 3번째 검사 직후 중단. A 실패 → A 통과 → A 실패는 연속 1회다.
- 테스트 트리의 내용·추가·삭제·이름·권한·변경 시각을 검사하며, 파일 이벤트와 200ms 간격 검사로 실행 중 변경도 감지한다. 심볼릭 링크/특수 테스트 파일은 시작하지 않는다.
- Git HEAD와 테스트 인덱스가 바뀌어도 중단한다.
- 훅의 `guard: BLOCKED`, `verify: FAIL/BLOCKED` 등 차단 신호, Codex의 BLOCKED 보고·실행 오류는 더 이른 중단 사유다. 기존 훅을 끄거나 반복 실패를 우회하지 않는다. 따라서 훅이 차단하면 첫 바퀴에도 멈출 수 있다.
- Ctrl-C/SIGTERM은 자식 프로세스를 종료하고 중단 기록을 남긴다.

## 기록

기록 디렉터리는 `artifacts/loops/<시각>-<실행ID>/`이며 실행 시작 시 위치를 출력한다.

| 파일 | 내용 |
|---|---|
| `run.json`, `baseline-files.json` | 작업 설명·기준 커밋·예산·보호 파일 해시/메타데이터 |
| `baseline.json`, `baseline.vitest.json` | 수정 전 승인 테스트·타입 검사 결과 |
| `round-01.json` 등 | 바퀴별 명령·종료 코드·PASS/FAIL/BLOCKED/NOT_RUN·실패 이름·이유·연속 횟수·중단 사유 |
| `round-01.prompt.txt` 등 | 해당 바퀴의 구현 요청과 실패 근거 |
| `*.stdout.log`, `*.stderr.log` | Codex JSON 이벤트와 검사 출력. 알려진 환경 비밀값·결제키·인증 헤더를 마스킹 |
| `round-01.vitest.json` 등 | 전체 테스트의 파일·이름별 결과 |
| `summary.json` | 최종 상태·바퀴 수·경과 시간·중단 사유 |

실행 결과가 불완전하거나 수집된 테스트 집합이 기준과 다르면 PASS로 보고하지 않는다.
실제 환불·브라우저·토스 실연결 통과를 의미하지 않으며, 구현 범위는 작업 설명에 해당하는 승인된 순수 규칙이다.
파일 감시는 변경을 발견해 중단하는 장치이며 임의 코드 전체의 파일 쓰기를 막는 샌드박스를 대신하지 않는다.

## 1바퀴 BLOCKED 조사와 작업 절차 수정

`artifacts/loops/2026-10-12T00-30-08.924Z-dff2f5d5/round-01.json`과
`round-01.codex.stdout.log`에서 1바퀴 에이전트의 중단 보고를 확인했다.
에이전트는 `git status --short`와 `rg --files src/rules tests/rules .specify/memory`를
줄바꿈으로 묶은 셸 명령을 제출했고, PreToolUse 가드가
`보호 경로를 참조하는 복합 셸 명령은 허용하지 않습니다.`로 차단했다.
최종 중단 사유는 `agent_blocked`이며, 수정 후 테스트·타입 검사는 `NOT_RUN`이다.
기준 검사의 결제 테스트 실패는 구현 전 상태이며 이 차단의 원인이 아니다.

`scripts/loop.mjs`의 바퀴별 프롬프트에 다음 작업 절차를 추가했다.

- 셸 호출 하나에 단일 명령만 넣고 결과를 확인한 뒤 다음 호출을 한다.
- 문서·테스트 계약은 파일별 `cat`, 상태와 파일 탐색은 별도 `git status`·`rg` 호출로 읽는다.
- 읽기에도 줄바꿈·명령 연결·파이프·리다이렉션·명령 치환을 사용하지 않는다.
- 소스는 `src/rules` 대상 `apply_patch`로 수정한다.
- 실제 차단 후에는 명령을 분리해 재시도하지 않고 기존 규칙대로 중단한다.

가드·훅·검사 설정·승인 테스트·제품 코드는 변경하지 않았다.
횟수·시간 제한, 보호 파일 감시, 차단 시 즉시 중단 처리도 유지했다.
이번 수정의 검증은 아래에 별도로 기록하며, 과거 실행 기록을 수정하지 않는다.
