# ev-booking 작업 지침

## 작업 시작 전에 읽을 문서

이 폴더에서 작업을 시작하기 전에 다음 세 문서를 모두 먼저 읽는다.

1. [docs/prd.md](docs/prd.md): 제품 목적, 범위, 확정 정책, 열린 질문
2. [docs/acceptance.md](docs/acceptance.md): US별 GIVEN/WHEN/THEN 수용 기준과 조건부 기준
3. [docs/tasks.md](docs/tasks.md): 구현 작업, 관련 US·AC, 완료 조건, 선행 작업, 구현 전 확인 목록

## 정책과 작업 범위

- 문서에 없는 정책은 임의로 정하지 말고 사용자에게 물어본다. 금액, 시간 경계, 자격, 상태 전이, 대기 순서, 권한, 실패 처리도 이 원칙을 따른다.
- 문서끼리 충돌하거나 해석이 여러 가지면 관련 문서·US·AC·T 번호를 제시하고 사용자에게 확인한다. 작업 목록만으로 PRD·수용 기준의 정책을 바꾸지 않는다.
- 조건부 AC와 tasks.md의 C 항목은 미확정 상태이다. 단순 문서 승인만으로 확정됐다고 간주하지 않는다. 해당 동작을 구현하기 전에 답변을 받고 관련 문서를 함께 갱신한다.
- 기술 구성이 아직 확정되지 않았다면 T-01의 합의부터 수행한다. 제품 정책에 영향을 주지 않는 내부 구현 선택은 합의한 구성 안에서 결정할 수 있다.
- 요청받은 T 작업의 선행 조건과 실제 완료 근거를 확인하고, 그 작업의 범위와 완료 조건에 맞춰 수행한다. 필요한 추가 작업은 별도로 설명한다.

## 막혔을 때의 중단·보고 기준

- `tests` 경로를 참조하는 셸 명령은 하나씩 별도의 도구 호출로 실행한다. 다른 명령과 `&&`, `;`, 파이프 등으로 결합하거나 한 호출에 여러 명령을 넣지 않는다. 조회와 테스트 실행에도 적용한다.
- 복합 셸 명령 형식 때문에만 훅이 차단한 경우에는 사용자에게 다시 묻지 않고, 같은 작업을 명령 하나씩 별도의 도구 호출로 나누어 재시도할 수 있다. 작업 내용·대상 경로·권한은 바꾸지 않는다. 개별 명령도 차단되거나 형식 외 차단 사유가 있으면 즉시 멈추고 사용자에게 물어본다.
- 위 복합 명령 형식 예외를 제외하고, 훅이 실제로 명령·수정·작업 완료를 차단하면 즉시 멈추고 사용자에게 물어본다. 다른 도구·명령·경로로 같은 작업을 우회하거나 훅을 끄고, 훅·검사 설정을 바꾸어 통과시키지 않는다. 실제 차단을 동반한 자동 수정 요청도 사용자 답변 전에는 수정·재시도하지 않는다.
- **Stop 훅이 테스트 실패를 알려 주는 것 자체는 차단이 아니다.** `verify: FAIL`이나 구현 수정·재검증 요청만으로 `BLOCKED`로 판정하거나 사용자에게 다시 허가를 요청하지 않는다. 구현 중이면 승인된 작업 범위 안에서 테스트를 변경하지 않고 구현 수정·재검증을 계속한다. 정책 확인·테스트 변경 승인·같은 사례 세 번 연속 실패·실제 도구 차단의 중단 기준은 그대로 적용하며, Stop 훅이 실행한 실패도 해당 사례의 연속 실패 이력에 포함한다.
- 스크립트·문서 수정 등 제품 기능을 구현하지 않는 작업에서는 Stop 훅의 테스트 실패를 `FAIL`로 보고하고 요청받은 작업을 마무리한다. 실패를 없애려고 범위 밖의 제품 구현을 시작하지 않으며, 실제 수행한 구문·정적 검사 결과와 훅의 테스트 결과를 구분한다. 같은 실패가 다시 보고됐다는 이유만으로 완료 보고를 반복하거나 사용자 확인을 요구하지 않는다.
- 정책 때문에 테스트를 바꿔야 한다면 해당 구현을 중단하고 테스트를 직접 고치지 않는다. 관련 문서·US·AC·T·C 번호, 대상 테스트 파일·사례, 현재 기대값과 제안 기대값, 변경 이유와 영향 범위를 정리해 사용자에게 제시한다. 정책이 미확정이면 필요한 질문도 함께 적는다. 사용자 답변과 별도 테스트 변경 단계의 승인 전에는 테스트 변경을 시작하지 않으며, 변경 후에는 헌법의 사용자 테스트 확인 → 실패 확인 → 구현 절차를 다시 따른다.
- 같은 테스트 사례가 세 번 연속 실패하면 세 번째 실패 직후 수정·재실행을 멈추고 사용자에게 물어본다. 파일 경로와 테스트 이름으로 사례를 추적하고 각 실행 명령·실패 이유·시도한 수정 내용을 기록한다. 중간에 다른 테스트를 실행하거나 명령·도구를 바꿔도 그 사례의 연속 실패 횟수를 초기화하지 않는다. 훅 차단 등 더 이른 중단 기준이 있으면 세 번을 채우지 않고 즉시 멈춘다.
- 중단 보고에는 차단한 훅 또는 실패한 테스트, 관련 정책 근거, 비밀값을 제거한 오류 요약, 지금까지의 시도, 남은 변경 제안과 사용자가 결정할 사항을 포함한다. 실행 실패는 `FAIL`, 차단으로 진행하지 못한 작업은 `BLOCKED`, 실행하지 않은 검사는 `NOT_RUN`으로 구분하며 완료로 보고하지 않는다.
- 현재 하네스 구성과 검증 근거는 [docs/harness.md](docs/harness.md)를 참고한다. 세 번 연속 실패 집계는 에이전트가 실행 이력으로 관리하는 규칙이며 현재 훅에 자동 집계 기능이 있다고 간주하지 않는다.

## 예약·결제 도메인 규칙

- 예약금·결제·환불 금액은 원(KRW) 단위 정수로 저장·계산한다.
- 정책 시간의 표시·판정은 서울 시간(`Asia/Seoul`)의 문서상 시연용 시계를 따른다. 외부 결제 시스템 시간은 변경하지 않는다.
- 예약·결제 도메인 규칙 코드는 `src/rules`에만 순수 함수로 둔다. 화면·API에서 규칙을 중복 구현하지 않고 해당 모듈을 호출한다.
- 결제·환불은 토스페이먼츠 테스트 키와 테스트 모드만 사용한다. 실제 결제는 금지하며 인증키·비밀값을 코드, 문서, 로그에 노출하지 않는다.
- 상세 정책은 [docs/prd.md](docs/prd.md), 경계값·검증 기준은 [docs/acceptance.md](docs/acceptance.md), 구현 범위·선행 조건은 [docs/tasks.md](docs/tasks.md)를 따른다.

## 데이터·시연·검증

- 학습용 로컬 모바일 웹이다. 배포하지 않는다. 실제 충전소 이용·주차면·충전량을 보장하지 않는다.
- 충전소 원본은 `../ev-map/data`이다. 원본을 임의로 수정하거나 재수집하지 않는다.
- 관련 AC를 검증하고 `PASS / FAIL / BLOCKED / NOT_RUN`을 정확히 기록한다. 정적 확인, 모의 처리, 브라우저 검증, 토스 테스트 실연결을 구분하며 실행하지 않은 검사를 통과로 보고하지 않는다.
