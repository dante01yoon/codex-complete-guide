# 서울 전기차 충전소 가상 예약 서비스 PRD

- 문서 상태: 초안
- 작성일: 2026-10-05
- 프로젝트: `ev-booking`
- 목적: 학습용 로컬 시연. 실제 서울 충전소 데이터에 가상 예약 기능을 결합한다.
- 사용자 정책 답변 반영: 4차 초안 (2026-10-11 카드 결제·DONE·점유 만료·늦은 승인·환불 실패 정책 추가)
- 유저 스토리별 수용 기준: [acceptance.md](acceptance.md). 문서의 기준은 검증 요구사항이며 실제 실행 결과가 아니다.

## 1. 배경과 문제

운전자가 충전소를 찾아도 도착 시점에 충전기를 사용할 수 있는지 알기 어렵다. 예약 후 방문하지 않는 사용자가 있으면 다른 운전자의 이용 기회도 줄어든다. 운영자는 예약 현황을 확인하고 고장·점검 발생 시 이용을 차단하거나 예약을 취소할 수 있어야 한다.

위 문제는 제품이 해결하려는 가설이며, 실제 운전자·운영자 인터뷰로 검증된 결과는 아니다. 이 서비스는 실제 충전소의 이용 권한을 확보하거나 현장 이용을 보장하지 않는다. 저장된 서울 충전소 정보를 기반으로 예약금, 예약, 체크인, 노쇼, 대기자 승계를 시연한다.

### 1.1 운전자의 문제

- 이용할 수 없는 충전소에 방문하는 헛걸음을 줄이고 싶다.
- 이용 제한, 충전기 상태, 정보 수집 시점을 예약 전에 확인하고 싶다.
- 자기 차량의 커넥터 종류를 직접 선택하고 해당 커넥터를 지원하는 충전기만 예약하고 싶다.
- 특정 충전기의 이용 시간을 예약하고 예약·결제·취소 결과를 확인하고 싶다.
- 원하는 시간이 이미 예약되어 있으면 대기하고, 빈자리가 생겼을 때 이용 기회를 받고 싶다.
- 취소 시점에 따른 예약금 환불 조건을 알고 싶다.

### 1.2 운영자의 문제

- 담당 충전소의 예약 현황을 확인해야 한다.
- 고장이나 점검 중인 충전기에 신규 예약이 들어오는 것을 막아야 한다.
- 운영상 사유로 예약을 취소하고 예약금을 전액 환불해야 한다.
- 노쇼로 비게 된 이용 시간을 대기자에게 넘겨야 한다.

### 1.3 데이터 근거와 한계

데이터 원본은 `../ev-map/data`의 저장된 JSON 파일이다. 이번 확인 시점의 구성은 다음과 같다.

| 파일 | 내용 | 제품에서의 역할 |
|---|---|---|
| `stations.json` | 서울 충전기 75,891건, 충전소 ID 기준 13,000곳. 각 레코드에 38개 필드 | 충전소·충전기 정보와 예약 대상 식별 |
| `status.json` | 최근 상태 변경분 1,454건, 각 9개 필드 | 원본보다 최신인 충전기 상태 반영 |
| `dashboard.json` | 충전소별 집계와 수집·생성 시각 메타데이터 | 지도·통계 표시 및 수집 시각 안내 참고 |

- 충전기는 `statId`와 `chgerId`의 조합으로 식별한다.
- 원본에 위치, 운영기관, 운영시간, 충전기 유형·출력, 상태, 이용 제한, 삭제 여부가 포함되어 있다.
- `limitYn=Y`인 충전기는 47,810건, `delYn=Y`인 충전기는 657건이다. 두 집합은 겹칠 수 있다.
- `status.json`은 전체 충전기의 실시간 상태가 아니라 조회 당시 최근 변경분이다. 같은 충전기의 유효한 `statUpdDt`가 원본보다 최신인 경우에 반영한다.
- 기존 데이터 프로젝트는 상태 코드 `2`를 충전대기, `3`을 충전중, `4/5`를 고장·점검, 나머지를 확인 불가로 분류한다.
- `useTime`은 자유 형식 문자열이며 누락도 있다. 24시간 이용 안내가 있는 충전기만 예약 대상으로 한다. 24시간 안내의 문자열 판별 범위는 열린 질문에 남긴다.
- 예약 시간표, 예약금, 결제, 사용자, 운영자 권한, 대기 목록은 원본에 없으므로 서비스에서 별도로 관리한다.
- 실제 이용 가능 여부를 검증하지 않으며, 데이터 수집 시각과 개별 상태 갱신 시각을 구분한다. 충전대기 표시만으로 현장 이용을 보장하지 않는다.

## 2. 목표와 성공 지표

### 2.1 목표

1. 이용 제한·삭제·고장·점검·상태 확인 불가 충전기를 예약에서 제외하여 운전자의 헛걸음을 줄인다.
2. 예약금과 체크인 기한을 통해 노쇼를 줄이는 흐름을 시연한다.
3. 취소·노쇼로 생긴 이용 기회를 첫 번째 대기자에게 자동 승계하는 흐름을 시연한다.
4. 운영자가 담당 충전소의 예약과 점검·고장 상황을 관리하도록 한다.

### 2.2 성공 지표

| 지표 | 산정 방식 | 정책 |
|---|---|---|
| 예약 이행률 | 체크인한 평가 대상 예약 수 ÷ 평가 대상 예약 수 × 100 | 이용 종료 여부가 아니라 체크인 기준 |
| 노쇼율 | 노쇼 처리된 평가 대상 예약 수 ÷ 평가 대상 예약 수 × 100 | 사용자 취소·운영자 취소는 분모에서 제외. 노쇼에 따른 자동 취소는 노쇼로 포함 |

목표치는 두지 않는다. 미래 예약과 아직 체크인 기한이 지나지 않은 미체크인 예약은 판정 대기이며, 분모에 넣지 않는 것을 초안 기준으로 한다. 확정되지 않은 결제 대기·임시 점유·대기 신청도 예약 실적에 포함하지 않는다. 승계 후 결제 확정된 예약은 별개의 예약 기록으로 집계한다. 체크인 후 사용자 취소는 취소 제외 규칙을 우선하여 분자와 분모에서 함께 제외한다. 이러한 집계 해석과 분모가 0일 때의 표시는 열린 질문에서 확인한다.

시연 데이터와 테스트 계정의 기록으로 지표를 산출한다. 실제 운전자의 헛걸음이나 노쇼 감소 효과를 검증했다고 해석하지 않는다.

## 3. 대상 사용자

| 사용자 | 목적 | 권한 |
|---|---|---|
| 일반 운전자 역할의 테스트 계정 | 충전기 검색, 예약, 결제 시연, 체크인·종료, 취소, 대기 신청 | 자신의 예약·대기·결제 결과 확인 및 허용된 조작 |
| 운영자 역할의 테스트 계정 | 담당 충전소 예약 확인과 운영상 차단·취소 | 담당 충전소의 예약 목록 조회, 충전기 점검 차단, 예약 취소 |

운전자 테스트 계정 3개, 운영자 테스트 계정 1개, 운영자 담당 충전소 1곳으로 시연한다. 시연은 테스트 계정으로 로그인한다. 실제 운영기관의 계정이나 관리 권한을 사용하지 않으며, 테스트 운영자와 담당 충전소의 연결은 시연용 설정으로 관리한다.

## 4. 범위와 범위 밖

### 4.1 이번 버전의 범위

- 로컬에서 실행하는 모바일 웹. 외부 배포는 하지 않는다.
- 저장된 서울 충전소·충전기 정보 조회와 데이터 수집 시각 표시.
- 이용 제한이 없고 삭제되지 않았으며 24시간 이용 안내가 있는 충전기만 예약 대상으로 사용.
- 고장·점검·상태 확인 불가 및 운영자가 점검 차단한 충전기의 예약 금지.
- 운전자가 자기 차량의 커넥터 종류를 직접 선택하고, 대응표상 이를 지원하는 충전기만 예약.
- 특정 충전기의 이용 시간 예약과 예약 목록 조회.
- 토스페이먼츠 테스트 모드로 예약금 3,000원 결제 및 환불 시연.
- 취소 시점별 환불, 운영자 취소 시 전액 환불.
- 체크인·이용 종료 버튼, 예약 종료 시각의 자동 종료·전액 환불, 체크인 기한 도달 시 노쇼 처리.
- 같은 충전기·시작·종료 시각의 예약에 대한 대기 신청. 사용자 취소·노쇼 발생 시 순서대로 결제 기회를 제공하고 결제 승인 후 승계 확정.
- 운영자 담당 충전소 예약 목록, 점검 차단·해제, 개별 예약 취소.
- 화면 안에서 예약·결제·환불·대기·운영자 취소 결과 안내.
- 예약 이행률과 노쇼율 산출을 위한 시연 기록.
- 시간 경과와 자동 처리를 보여 줄 시연용 시계.

### 4.2 확정된 정책

모든 예약·취소·체크인·노쇼·대기 기한은 서울 시간(`Asia/Seoul`, UTC+09:00)의 시연용 시계를 기준으로 표시·판정한다. 토스페이먼츠 외부 테스트 시스템의 시간은 시연용 시계로 변경하지 않는다.

| 항목 | 정책 |
|---|---|
| 서비스 성격 | 학습용 로컬 모바일 웹. 실제 서울 데이터 위의 가상 예약이며 배포하지 않음 |
| 예약 대상 | `limitYn=N`, `delYn=N`, 24시간 이용 안내. 유효 상태가 충전대기(`2`) 또는 충전중(`3`)이고 운영자 점검 차단이 없는 충전기 |
| 커넥터 조건 | 운전자가 직접 선택한 자기 차량의 커넥터를 지원하는 `chgerType`만 예약 가능. 1.4 대응표를 적용하며 기존 자격·시간·권한 제한도 모두 충족해야 함 |
| 상태 제한 | 고장·점검(`4/5`)·상태 확인 불가(그 외)는 예약 금지. 충전중이어도 미래 예약 허용 |
| 보장 범위 | 특정 충전기 이용 시간만 가상 예약. 주차면·충전량 보장 없음 |
| 예약 가능 기간 | 현재 시각 이상, 현재 시각 + 7일 이하의 시작 시각. 종료 시각은 7일을 넘어도 됨 |
| 시간 단위·길이 | 매시 00분·30분 시작, 1회 30·60·90분 |
| 임시 점유·확정 | 결제창을 열면 해당 시간 구간을 임시 점유하며 생성 + 정확히 10분에 만료. 기한 미만에 카드 결제 DONE과 유효한 자리 확보를 확인해야 예약 확정 |
| 결제 보호 | 같은 결제를 중복 처리하지 않음. 결제 후 자리 확보 실패 시 3,000원 전액 환불 |
| 금액 검증 | 서버에 저장한 주문의 예약금 3,000원과 요청 금액을 비교. 불일치·KRW 정수 조건 위반은 승인 요청 전에 거절. 승인 결과의 주문·금액·통화도 검증 |
| 결제수단·완료 | 카드만 허용. 검증된 Payment 객체의 status가 DONE일 때만 결제 완료. 성공 페이지 도착이나 다른 상태만으로 완료하지 않음 |
| 늦은 승인 | 임시 점유 만료 시각 이상에 처음 확인된 승인(DONE)은 예약 없이 3,000원 전액 환불. 이미 처리한 같은 결제는 다시 확정·환불하지 않음 |
| 환불 실패 | 실패하면 세 번까지 다시 시도하고 실패가 지속되면 운영자 확인 필요로 기록. 성공 확인 전 환불 완료로 표시하지 않음. 최초 요청 포함 여부·재시도 간격·응답 불명 복구는 열린 질문 6에서 별도 확인 |
| 진행 중 예약 | 결제 완료부터 이용 종료 또는 취소 전까지. 사용자당 1건 |
| 대기 제한 | 진행 중 예약과 별도로 사용자당 1건. 대기 신청 시 결제 없음 |
| 대기 대상·순서 | 같은 충전기의 원래 시작·종료 시각이 모두 동일한 예약에 연결. 신청 시각 순서 |

| 정상 이용 반환 | 체크인한 예약은 이용 종료 시 3,000원 전액 반환. 종료 버튼을 누르지 않으면 예약 종료 시각에 자동 종료·전액 반환 |

### 4.2.1 상태와 시간 처리

- 예약 임시 점유·결제 대기와 결제 승인으로 확정된 예약을 구분한다. 결제 대기 중에는 이용 확정으로 표시하지 않는다.
- 대기 승계의 자동 처리는 결제 요청까지이며, 대기자는 직접 테스트 결제를 완료해야 확정된다.
- 예약 시간은 시작 포함·종료 제외 구간으로 해석한다. 같은 충전기의 겹치는 확정 예약·유효 임시 점유를 중복 생성하지 않는다. 연속한 두 예약의 종료·시작 시각이 같으면 겹치지 않는다.
- 노쇼 자동 취소와 사용자 취소는 별도 사유로 기록한다. 노쇼를 사용자 취소로 집계하여 지표에서 제외하지 않는다.
- 체크인하지 않은 예약을 자동 정상 종료하여 예약금을 돌려주지 않는다. 일반 예약은 먼저 시작 + 15분에 노쇼 처리한다.
- 버튼과 시간 경과 이벤트가 반복되어도 같은 예약의 종료·취소·노쇼·결제·환불을 중복 반영하지 않는다.
- 일반 예약의 임시 점유는 정확히 생성 + 10분에 만료한다. 만료 시각과 같은 시각의 첫 승인 확인도 늦은 승인으로 처리하여 예약 없이 전액 환불한다. 승인·웹훅 재전달은 원래 처리 결과를 유지한다.
- 토스 인증 유효시간(인증 후 실제 시간 10분)과 서비스 점유 기한(생성 후 시연용 시간 10분)은 별개이다. 외부 승인 시각이나 웹훅 생성 시각으로 서비스 점유 기한을 연장하지 않는다.
- 승계 결제 요청은 정확히 요청 +10분에 만료한다. 같은 시각의 첫 승인 확인도 늦은 승인으로 전액 환불한다. 노쇼 승계의 잔여시간은 요청과 승인 확인 시 모두 재검사하며 정확히 30분은 허용하고 미만은 승계하지 않는다. 승인 시 미달이면 전액 환불한다. 반복 결제 결과로 환불을 중복 요청하지 않는다.
- 시작 전 승계 체크인 기한은 원래 시작 +15분으로 판정한다(2026-10-11 사용자 답변, C-02). 사용자 취소 승계의 최소 잔여시간 적용, 재개방·복구 등 답변하지 않은 항목은 열린 질문에 남긴다.

### 4.2.3 승인·웹훅 검증 범위 (15장 실습)

- 승인 전 주문 금액 검증과 승인 결과의 카드·DONE·기한·중복 판정을 테스트부터 작성한다. 기존 예약 자격·권한 검사도 유지한다.
- 카드 상태 알림은 PAYMENT_STATUS_CHANGED를 대상으로 한다. 서버 결제 조회로 검증된 결과에 같은 결제 규칙을 적용하고, 승인 응답과 웹훅이 같은 결제를 전달해도 한 번만 반영한다.
- 웹훅 본문만으로 결제 완료·예약 확정을 만들지 않는다. 이 이벤트에는 지급대행용 HMAC 서명이 있다는 가정을 하지 않는다. HTTP 수신·실제 조회·응답 코드·웹훅 재전송 처리는 별도 통합 작업이다.
- 테스트는 토스 응답·조회 결과를 로컬 fixture로 대체한다. 실제 승인·조회·취소 API 호출, 웹훅 등록, 배포는 이번 요청 범위 밖이다.
- 공식 근거: [Payment 상태·승인 API](https://docs.tosspayments.com/reference), [서버 금액 검증](https://docs.tosspayments.com/guides/v2/get-started/llms-quick-reference), [웹훅 이벤트](https://docs.tosspayments.com/reference/using-api/webhook-events).

### 4.2.2 운전자 선택 커넥터와 예약 자격

- 차량 모델을 자동 판별하지 않고 운전자가 자기 차량의 커넥터 종류를 직접 선택한다.
- 선택한 커넥터가 1.4 대응표의 지원 종류에 포함된 충전기만 예약할 수 있다.
  지원하지 않는 충전기는 예약을 거절하고 커넥터 불일치 사유를 안내한다.
- 복합 타입은 포함된 종류 중 선택 커넥터를 지원하면 커넥터 조건을 만족한다.
  커넥터 일치만으로 이용 제한·삭제·운영시간·상태·운영자 차단·시간 충돌 조건을 우회하지 않는다.
- 선택값의 저장·변경 시점, 대기·승계 중 선택 변경, 어댑터 사용과 버스전용 자격 등
  새 정책에서 정하지 않은 세부 사항은 열린 질문 9와 tasks.md C-11에서 확인한다.

### 4.2.4 MCP 결제 링크의 시연 서버 연결 (2026-10-12 사용자 요청)

- 승인된 유효 점유의 `/payment/<holdId>` 주소를 기존 15장 로컬 결제 시연 서버(5180)에 연결한다.
  점유의 충전기·선택 커넥터·예약 시간·생성/만료·예약금3,000원/KRW를 해당 주문에 유지한다.
- 페이지와 직접 주문 API는 신뢰된 소유자·승인 파일·점유 기한을 다시 확인한다.
  미승인·없는 점유·권한 없음·만료이면 결제 화면 대신 이유를 안내하며 결제 위젯을 시작하지 않는다.
  정확히 생성+10분부터 만료한다. 페이지 재조회로 기한을 연장하거나 다른 주문을 새로 만들지 않는다.
- 결제 클릭 직전에도 조회 게이트를 확인한다. 외부 인증을 이미 끝낸 늦은 승인 결과는
  기존 카드/DONE·금액·중복·전액 보상 규칙으로 처리한다.
- 이번 요청은 HTTP 주문 연결 범위이다. 실제 승인·환불, 전체 MCP 확정 예약 저장·웹훅·로그인·복구의
  완료를 의미하지 않는다. 실행 근거는 [mcp-payment-page-validation.md](mcp-payment-page-validation.md)이다.

### 4.3 범위 밖

- 외부 배포와 실제 충전소 예약·현장 이용 보장.
- 실제 금전 결제·환불, 충전비·주차비 결제.
- 실제 운영기관과의 계약·운영자 신원 검증.
- 차량 모델 기반 자동 호환 판별. 운전자가 직접 선택한 커넥터와 코드 대응에 따른 예약 제한은 이번 범위에 포함한다.
- 충전기 원격 제어와 실제 충전 시작·종료 감지.
- 주차면 확보와 충전량 보장.
- 초과 이용 처리. 다음 버전에서 검토한다.
- 문자·이메일·푸시 등 외부 알림.
- 실시간 공공데이터 API 연동과 자동 데이터 재수집.

## 6. 열린 질문

기존 14개 질문의 답변은 위 정책에 반영했다. 다음은 답변을 조합할 때 남는 경계 조건이다. 관련 수용 기준은 조건부로 표시한다.

1. **승계 결제 후 잔여시간 재검사 (부분 확정, 2026-10-11 사용자 답변):** 노쇼 승계는 요청과 승인 확인 시 모두 원래 종료까지 30분 이상이어야 한다. 정확히 30분은 허용하고 미만은 승계하지 않으며, 승인 시 미달이면 3,000원 전액 환불한다. 미정: 최소 30분 제한을 사용자 취소 이후 승계에도 적용하는가?
2. **미래 예약의 조기 승계 체크인 (확정, 2026-10-11 사용자 답변):** 시작 전에 승계가 확정되면 원래 예약처럼 원래 시작 시각을 기준으로 한다. 체크인 구간은 시작 10분 전 이상~시작 15분 후 미만이며, 정확히 시작 +15분에 미체크인 노쇼 처리한다. 시작 후 승계의 확정 +15분 규칙은 유지한다.
3. **진행 중 예약이 있는 첫 대기자:** 별도 대기는 허용하지만 승계 시 진행 중 예약 1건을 넘길 수 없다. 첫 대기자가 이미 진행 중 예약을 보유하면 건너뛸지, 기회를 보류할지 결정해야 한다.
4. **기한 동시성 (부분 확정):** 일반 임시 점유와 승계 결제 요청은 정확히 생성·요청 +10분에 만료하고, 만료 시각 이상에 처음 확인한 승인은 예약 없이 전액 환불한다. 승계의 정확히 10분 경계는 2026-10-11 사용자 답변으로 확정했다. 미정: 승계 결제 요청 재개방, 일반 결제가 시작 +15분 이후 기한 내 승인되는 경우, 예약 종료·승계 체크인 기한 동시 도달의 우선순위.
5. **24시간 안내 판별:** `24시간 이용가능`, `24시간`, `00:00~24:00`을 모두 허용할 것인가? 제한 안내가 섞인 문구·공백·누락·모호한 문구의 처리와 시연 담당 충전소를 선택해야 한다.
6. **동률·대기 철회·결제 실패 (부분 확정):** 환불 실패는 세 번까지 다시 시도하고 계속 실패하면 운영자 확인 필요로 둔다. 미정: 최초 요청 포함 여부, 재시도 간격·재시작 시 횟수 유지·응답 불명 복구, 대기 동률 보조 정렬·철회, 결제 실패 시 기한 내 재시도·창 닫기 해제, 운영자 취소·차단과 진행 중 결제의 경합.
7. **지표 상세:** 판정 대기 예약 제외, 승계 예약 별도 집계, 체크인 후 취소 시 분자·분모 동시 제외라는 초안 해석을 확인해야 한다. 분모 0은 `집계 대상 없음`으로 표시하고 시연용 시계 기준 전체 기록을 집계할 것인가?
8. **시연용 시계의 적용:** 모든 정책 타이머를 같은 시계에 연결하되 외부 테스트 결제 시스템의 시간은 유지하는 해석을 확인해야 한다. 시계 역행·초기화와 앱 종료 중 지난 이벤트 재처리는 별도 결정이 필요하다.

9. **커넥터 선택의 세부 동작:** 선택값은 예약마다 입력하는가, 계정에 저장하는가? 선택하지 않았거나 코드가 누락·미정의인 경우의 안내는? 결제·대기·승계 중 선택 변경은 어떻게 처리하는가? 어댑터 사용을 허용하는가? 가이드의 DC콤보2(버스전용) 선택에 별도 차량 자격을 요구하는가? 기본 호환 제한은 확정됐지만 이 세부 동작은 미정이다.

#### 날짜·시작 시각 입력 확장 합의 (T-59, 2026-10-12 사용자 답변)

- 사용자가 “이 계약으로 진행”을 선택했다. `search_chargers`는 `date:YYYY-MM-DD`와

  날짜는 실제 달력의 유효한 날짜, 시각은 24시간제이며 초·밀리초는 0이다.
- 기존 `timeText:'7시'` 단독 입력은 서울 시연용 오늘19시로 유지한다.
  두 입력 방식 혼용, 날짜/시각 중 한 필드 누락, 둘 다 없는 입력, 잘못된 날짜·시각·형식은 거절한다.

  마지막 허용 시작의 종료가 7일을 넘어도 된다. 명시 입력을 오늘19시로 덮어쓰지 않는다.

#### 초기 계획·순수 규칙 단계의 기록

아래는 처음 요청한 계획·테스트와 순수 규칙 단계의 범위 기록이다. 당시 미정이었던 승인 경로·MCP 구성과 계획 후 정지 범위는 위 실제 서버 추가 합의로 갱신됐다. 현재 요청은 새 테스트 확인·Red 후 구현·리뷰까지이며 실제 보호 승인 폴더의 사람 전용 경계는 유지한다.

- 충전기 검색, 10분 임시 점유, 결제 링크 요청의 도구 세 개를 제공한다. 도구명과 내부 함수명은 [mcp-booking-plan.md](mcp-booking-plan.md)의 기술 제안이다.
- 결제 링크는 사람이 승인했을 때만 생성한다. 승인 전에는 링크 대신 점유·예약금 요약과 `npm run approve -- <holdId>` 명령을 반환한다. 사용자가 터미널에서 해당 명령을 실행하면 승인 파일을 생성하며, 해당 점유의 승인 파일이 존재하고 점유가 유효할 때만 링크를 생성한다(사용자 추가 확정).
- 승인 폴더는 사용자의 가드로 보호한다. 모델이 도구 인수에 넣은 `approved: true` 등 자기 선언은 사람의 승인 근거가 아니다. 실제 승인 폴더 경로·파일 규약·MCP 연결은 미정이며 이번에는 명령 실행·파일 생성·가드 변경을 하지 않는다.
- 예문의 `7시`는 서울 시연용 시계의 오늘 저녁 19시, `근처`는 강남역 기준 반경 1km이다. 이미 지난 오늘 19시를 임의로 내일로 바꾸지 않고 기존 예약 기간 조건을 적용한다.
- 점유가 끝나면 결제 링크도 사용할 수 없다. 링크 유효기한은 점유 기한을 넘지 않는다. 링크 생성은 결제 완료나 예약 확정이 아니다.
- 기존 커넥터·예약 자격·시간·겹침·테스트 결제 정책을 유지한다. 이번은 계획과 확정 부분의 테스트 작성 후 사용자 확인까지만 수행한다. 테스트 실행·제품 구현·실제 링크 생성·토스 호출은 진행하지 않는다.
- C-12와 C-14·15의 위 서버 범위 합의는 확정됐다. 예문 외 자연어(C-13), 다른 운영시간 문구, 전체 로그인·복구·실제 결제 페이지는 미정/후속으로 유지한다. 기존 결제창 생성 점유 흐름과 별개로 이번 MCP의 독립 점유 생성 정책을 적용한다.
