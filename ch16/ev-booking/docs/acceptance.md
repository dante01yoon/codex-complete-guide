# 서울 전기차 충전소 가상 예약 서비스 — 수용 기준

- 문서 상태: 초안. [prd.md](prd.md)의 정책과 US-01~US-17에 대응한다.
- 작성일: 2026-10-05
- 이 문서는 구현 후 검증할 기준이다. 기존 규칙의 부분 검증과 결제 기능 검증을 구분한다. 2026-10-11 결제 정책 갱신은 기능 검증 통과를 뜻하지 않는다.
- `AC-07-1`은 US-07의 첫 번째 수용 기준을 뜻한다.
- 날짜와 시각은 모두 서울 시간 `Asia/Seoul`(UTC+09:00)의 시연용 시계 기준이다. 아래 초 단위 예시는 임계값을 확인하는 사례이며, 정책 비교는 정확한 시각으로 한다.
- 예약 구간은 `[시작, 종료)`로 해석한다. 결제 승인이 확인된 예약만 확정이며, 대기 신청과 임시 점유는 확정 예약이 아니다.
- 금액은 토스페이먼츠 테스트 모드의 원화 금액이다. 실제 금전 이동은 없다.
- **조건부** 기준은 사용자 답변에서 남은 경계 해석을 명시한 것이다. PRD 열린 질문 확정 전에는 최종 기준으로 간주하지 않는다.

### 단일 주문 시연의 승인된 확인 범위

2026-10-11 사용자 답변에 따라 5180 시연의 통합 테스트는 화면 확인으로 대체한다.
AC-05-1의 주문 정보·위젯, AC-05-7의 서버 금액 조작 거절,
AC-05-6·AC-06-2의 미완료 결과 화면을 이번 시연 범위에서 확인한다.
승인 처리에는 기존 AC-05-2·4·8·9 규칙을 그대로 호출한다.
실제 승인·환불 완료는 실제 응답을 확인한 경우에만 PASS로 기록한다.
AC-05-10은 이번 시연에서 환불 최초 요청 실패/응답 불명 시 `운영자 확인 필요`를
표시하고 자동 재시도를 보류한다. 전체 서비스의 재시도 횟수·간격 정책은 확정하지 않는다.
전체 앱의 자격·로그인·운영자·대기 검증을 대신하지 않는다.

사용자의 시연 버그 수정 요청에 따른 AC-05-6·AC-06-2 확인 부분:
인증 실패 반환 URL의 `code`·`message`와 SDK 오류의 같은 필드를 읽어 코드·사유를
텍스트로 표시한다. 실패 정보는 결제 완료·서버 승인 결과로 간주하지 않는다.
URL을 정리해도 새로고침 시 표시가 유지되며, 없는 정보를 추정해 채우지 않는다.
주문 조회 실패가 인증 실패 정보 표시를 가리지 않는다. 비밀값은 제거하고 HTML로 실행하지 않는다.

## US-01 — 충전소·충전기 조회

### AC-01-1 — 저장된 데이터 조회
- **GIVEN** `../ev-map/data/stations.json`이 정상적으로 준비되어 있다.
- **WHEN** 운전자가 충전소 목록과 특정 충전기 상세를 조회한다.
- **THEN** 저장된 이름·주소·위치·충전기 유형·출력·이용시간을 표시하고, 충전기를 `statId + chgerId`로 식별한다. 누락값은 정보 없음으로 표시하며 임의의 사양을 만들지 않는다.

### AC-01-2 — 가상 예약 안내
- **GIVEN** 운전자가 충전소 상세 또는 예약 화면을 보고 있다.
- **WHEN** 서비스 성격과 예약 보장 범위를 확인한다.
- **THEN** 학습용 가상 예약이며 실제 충전소 이용, 주차면, 충전량을 보장하지 않는다고 안내한다.

## US-02 — 예약 자격·상태·수집 시각

### AC-02-1 — 예약 대상 충전기
- **GIVEN** 충전기가 `limitYn=N`, `delYn=N`이고 `useTime=24시간 이용가능`이며 유효 상태가 `2`이고 운영자 차단이 없다.
- **WHEN** 차량 커넥터를 선택했고 해당 충전기가 그 커넥터를 지원하며 충돌 없는 미래 시간을 선택한다.
- **THEN** 예약 진입을 허용한다. 같은 조건에서 상태가 `3`(충전중)이어도 미래 예약을 허용한다.

### AC-02-2 — 이용 제한·삭제·운영시간 제외
- **GIVEN** 충전기가 `limitYn=Y`, `delYn=Y`, 또는 `useTime=09:00~18:00` 중 하나 이상에 해당한다.
- **WHEN** 운전자가 예약을 시도한다.
- **THEN** 예약을 막고 해당 사유를 표시한다. 제한이 없거나 삭제되지 않았다는 조건 하나만으로 허용하지 않는다.

### AC-02-3 — 고장·점검·상태 불명 제외
- **GIVEN** 유효 상태가 `4`, `5`, `1`, `9` 또는 해석할 수 없는 코드인 충전기이다.
- **WHEN** 미래 예약을 시도한다.
- **THEN** 상태에 따라 고장·점검 또는 상태 확인 불가를 안내하고 예약을 막는다.

### AC-02-4 — 최신 상태 병합과 시각 표시
- **GIVEN** 같은 `statId + chgerId`의 원본 상태와 변경분이 있고 변경분의 유효한 `statUpdDt`가 더 최신이다.
- **WHEN** 충전기 정보를 표시한다.
- **THEN** 최신 변경분의 상태를 적용한다. 더 오래된 변경분으로 덮어쓰지 않는다. 파일 수집 시각과 상태 갱신 시각을 구분하고 실시간 현장 정보로 표현하지 않는다.

### AC-02-5 — 24시간 문구 판별 경계 [조건부]
- **GIVEN** 이용시간이 `24시간`, `00:00~24:00`, 빈 문자열 또는 제한 안내가 섞인 문구이다.
- **WHEN** 예약 자격을 판정한다.
- **THEN** PRD 열린 질문 5에서 확정한 판별 규칙을 적용한다. 이 기준은 문자열 허용 목록 확정 전에는 판정하지 않는다.

### AC-02-6 — 선택 커넥터 일치·불일치
- **GIVEN** 운전자가 자기 차량의 커넥터로 DC콤보를 선택했고 다른 예약 자격과 시간 조건은 충족한다.
- **WHEN** `chgerType=04`와 `chgerType=01` 충전기에 각각 예약을 시도한다.
- **THEN** `04`는 커넥터 조건을 만족하여 예약 진입을 허용하고, `01`은 지원하지 않으므로 예약을 거절하고 불일치 사유를 안내한다. 실제 현장 이용을 보장하지 않는다.

### AC-02-7 — 공식 코드 대응과 복합 타입
- **GIVEN** PRD 1.4의 활용가이드 v1.25 대응표와 운전자가 선택한 커넥터가 있다.
- **WHEN** 지원 여부를 판정한다.
- **THEN** DC차데모는 `01/03/05/06`, AC완속은 `02`, AC3상은 `03/06/07`, DC콤보는 `04/05/06/08/10`, NACS는 `09/10`, DC콤보2(버스전용)는 `11`에 대응한다. `06`은 DC차데모·AC3상·DC콤보 각각을 지원하며 NACS는 지원하지 않는다. `10`은 DC콤보·NACS를 지원한다. 이 대응만으로 버스전용 차량 자격이나 어댑터 지원을 확정하지 않는다.

### AC-02-8 — 기존 예약 제한과 함께 적용
- **GIVEN** 선택 커넥터는 일치하지만 이용 제한·삭제·24시간 조건 불충족·고장·점검·상태 불명·운영자 차단 중 하나에 해당한다.
- **WHEN** 예약을 시도한다.
- **THEN** 기존 기준에 따라 예약을 거절한다. 커넥터 일치만으로 기존 자격 제한을 우회하지 않는다.

### AC-02-9 — 커넥터 선택의 세부 동작 [조건부]
- **GIVEN** 커넥터 미선택, 충전기 타입 누락·미정의, 선택값 저장·변경, 결제·대기·승계 중 변경, 어댑터 사용 또는 버스전용 차량 자격 판정이 필요하다.
- **WHEN** 해당 동작의 기준을 결정한다.
- **THEN** PRD 열린 질문 9와 C-11의 사용자 답변을 받은 뒤 구체적인 기준을 추가한다. 기본 정책 추가만으로 세부 처리까지 확정됐다고 간주하지 않는다.

## US-03 — 테스트 로그인과 계정별 제한

### AC-03-1 — 시연 계정 구성
- **GIVEN** 시연 계정이 준비되어 있다.
- **WHEN** 로그인할 계정과 운영자 담당 범위를 확인한다.
- **THEN** 운전자 계정 3개, 운영자 계정 1개, 운영자 담당 충전소 1곳을 제공한다. 예약·대기·운영자 조작은 로그인 계정의 권한으로 처리한다.

### AC-03-2 — 진행 중 예약 1건
- **GIVEN** 운전자가 결제 완료 후 아직 종료·취소되지 않은 예약 1건을 보유한다.
- **WHEN** 다른 예약을 결제·확정하려 한다.
- **THEN** 진행 중 예약을 2건으로 늘리지 않고 제한 사유를 안내한다. 결제 대기와 미승계 대기를 결제 완료 예약으로 집계하지 않는다.

### AC-03-3 — 예약 종료·취소 후 제한 해제
- **GIVEN** 운전자의 유일한 진행 중 예약이 이용 종료되거나 사용자 취소·운영자 취소·노쇼 취소되었다.
- **WHEN** 새 예약을 시도한다.
- **THEN** 진행 중 예약 1건 제한에 의한 차단을 해제한다.

### AC-03-4 — 소유자 권한
- **GIVEN** 운전자 A의 예약·대기 신청이 있다.
- **WHEN** 운전자 B가 A의 예약 조회·취소·체크인·종료 또는 대기 조작을 시도한다.
- **THEN** B에게 A의 개인 예약 정보와 조작 권한을 제공하지 않는다.

## US-04 — 예약 시간과 중복 방지

### AC-04-1 — 7일 시작 경계
- **GIVEN** 시연용 현재 시각이 `2026-10-05 10:00:00`이다.
- **WHEN** 예약 시작을 선택한다.
- **THEN** `2026-10-05 10:00:00`과 `2026-10-12 10:00:00`은 기간 조건상 허용하고, `2026-10-05 09:30:00`과 `2026-10-12 10:30:00`은 거절한다. 마지막 허용 시작의 90분 예약은 종료가 `2026-10-12 11:30:00`이어도 기간 조건상 허용한다.

### AC-04-2 — 시작 단위와 이용 길이
- **GIVEN** 예약 가능한 충전기와 기간이다.
- **WHEN** 시작 시각과 이용 길이를 입력한다.
- **THEN** 시작은 매시 `00분 00초` 또는 `30분 00초`, 길이는 `30분`, `60분`, `90분`만 허용한다. `10:15:00` 시작, `15분`, `45분`, `120분` 이용은 거절한다. 노쇼 승계 잔여시간은 US-11 규칙의 예외로 처리한다.

### AC-04-3 — 겹치는 시간 차단
- **GIVEN** 같은 충전기에 `10:00:00~11:00:00` 확정 예약 또는 유효 임시 점유가 있다.
- **WHEN** 다른 사용자가 `10:30:00~11:30:00`을 결제하려 한다.
- **THEN** 겹치는 시간을 확보하지 못하며 중복 확정을 막는다. `11:00:00~11:30:00`은 다른 제한이 없다면 연속 예약으로 허용한다.

### AC-04-4 — 동시 확보
- **GIVEN** 같은 충전기·시간이 비어 있고 운전자 2명이 동시에 결제창을 열려 한다.
- **WHEN** 시간 확보 요청을 처리한다.
- **THEN** 유효 임시 점유는 1건만 생성하며, 두 운전자의 예약을 같은 시간에 모두 확정하지 않는다.

## US-05 — 테스트 결제와 확정

### AC-05-1 — 금액과 안내
- **GIVEN** 운전자가 예약 결제를 시작하려 한다.
- **WHEN** 결제 조건을 확인하고 결제창을 연다.
- **THEN** 예약금 `3,000원`, 토스페이먼츠 테스트 결제, 취소 환불 `3,000원/1,500원/0원`, 노쇼 환불 `0원`을 안내한다. 충전비·주차비는 청구하지 않는다.

### AC-05-2 — 임시 점유와 승인
- **GIVEN** `10:00:00`에 결제창을 열어 `10:10:00`까지 해당 구간을 임시 점유했다.
- **WHEN** `10:09:59`에 `3,000원` 결제 승인과 유효한 자리 확보를 확인한다.
- **THEN** 예약을 확정하고 진행 중 예약으로 집계한다. 결제창 열기나 성공 화면 이동만으로 확정하지 않는다.

### AC-05-3 — 정확히 10분 만료
- **GIVEN** `10:00:00`에 생성된 임시 점유에 승인된 결제가 없다.
- **WHEN** 시연용 시계가 `10:10:00`에 도달한다.
- **THEN** 정확히 `10분`에 점유를 만료하고 시간을 해제한다. `10:09:59.999`까지 유효하며 `10:10:00.000`부터 유효하지 않다. 2026-10-11 사용자 답변으로 확정했다.

### AC-05-4 — 결제 중복 처리 방지
- **GIVEN** 같은 결제 식별자의 `3,000원` 승인을 처리하여 예약 1건을 확정했다.
- **WHEN** 동일 승인 결과가 2회 이상 전달되거나 다시 확인된다.
- **THEN** 예약은 1건, 결제 반영 금액은 `3,000원`으로 유지한다. `6,000원` 반영이나 예약 2건 생성이 발생하지 않는다.

### AC-05-5 — 결제 후 자리 확보 실패
- **GIVEN** `3,000원` 승인 결과가 확인됐지만 해당 구간을 확보할 수 없다.
- **WHEN** 예약 확정을 처리한다.
- **THEN** 이용 가능한 확정 예약을 만들지 않고 `3,000원` 전액 환불을 처리하며 실패와 환불 결과를 화면에 표시한다.

### AC-05-6 — 승인 없는 결제
- **GIVEN** 테스트 결제가 실패하거나 사용자가 결제창을 닫아 승인 확인이 없다.
- **WHEN** 예약 결과를 조회한다.
- **THEN** 확정 예약이나 `3,000원` 결제 완료로 표시하지 않는다. 만료 후 승인에는 AC-05-8, 환불 실패에는 AC-05-10을 적용한다. 점유 조기 해제·결제 재시도 등 미정 사항은 C-07에서 확정한다.

### AC-05-7 — 금액 조작 거절
- **GIVEN** 서버에 사용자·예약 구간과 연결한 주문 금액 `3,000원`, 통화 `KRW`를 저장했다.
- **WHEN** 클라이언트가 `100원`, `0원`, `-1원`, `3,000.5원` 또는 화면과 반환 URL을 함께 `100원`으로 바꿔 승인 요청을 보낸다.
- **THEN** 서버에 저장한 원화 정수 금액과 대조하여 승인 API 호출 전에 거절한다. 결제 완료·예약 확정·환불을 만들지 않는다. 정상 `3,000원` 요청만 금액 검증을 통과한다. 검증 기준을 클라이언트가 보낸 원래 금액으로 대체하지 않는다.

### AC-05-8 — 승인 확인 기한과 늦은 승인 보상
- **GIVEN** 임시 점유 생성 `10:00:00`, 만료 `10:10:00`이며 해당 결제는 아직 반영하지 않았다.
- **WHEN** 카드·KRW·3,000원·주문 식별자가 일치하는 DONE 결과를 서비스 시연용 시계로 확인한다.
- **THEN** `10:09:59.999`에는 자리·자격·1건 제한이 유효하면 확정한다. `10:10:00.000`, `10:10:00.001` 및 이후에는 자리가 여전히 비어 있어도 예약 없이 `3,000원` 전액 환불을 요청하고 결과를 기록한다. 외부 approvedAt·웹훅 createdAt이 기한 전이라는 이유로 만료한 점유를 되살리지 않는다. 재전달은 AC-05-4의 중복 보호를 적용한다.
- **외부 기한 구분:** 토스 인증 유효시간은 인증 후 실제 시간 10분이며 서비스 시계로 바꾸지 않는다. 외부 기한 만료로 DONE이 확인되지 않으면 AC-05-6·9에 따라 확정하지 않는다. 실제 API 기한 검증은 T-47의 실연결 범위이며 이번 로컬 테스트의 통과로 대신하지 않는다.

### AC-05-9 — 카드와 DONE만 결제 완료
- **GIVEN** 저장된 주문과 일치하는 결제 응답을 검증하고 있다.
- **WHEN** 결제수단과 Payment.status를 확인한다.
- **THEN** 결제수단은 `카드`만 허용하고 `status=DONE`일 때만 완료로 반영한다. `READY`, `IN_PROGRESS`, `WAITING_FOR_DEPOSIT`, `CANCELED`, `PARTIAL_CANCELED`, `ABORTED`, `EXPIRED` 및 알 수 없는 상태는 새 결제 완료·예약 확정의 근거가 아니다. 카드 외 수단은 완료로 수용하지 않는다. 취소 이력의 `cancelStatus=DONE`을 결제 승인 상태로 혼동하지 않는다. DONE이어도 AC-05-8의 점유 기한을 통과해야 예약을 확정한다.

### AC-05-10 — 환불 실패 재시도와 운영자 확인 [횟수 계산 조건부]
- **GIVEN** 늦은 승인 또는 자리 확보 실패로 `3,000원` 환불이 필요하다.
- **WHEN** 환불 요청이 실패한다.
- **THEN** 사용자 답변의 '세 번까지 다시' 범위 안에서 재시도하고 계속 실패하면 `운영자 확인 필요`로 기록한다. 성공을 확인하기 전 환불 완료로 표시하지 않는다. 실패한 환불 때문에 예약을 확정하지 않으며 중복 결과로 추가 환불하지 않는다.
- **남은 확인:** 최초 요청 실패 후 추가 3회인지, 최초 요청 포함 총 3회인지 C-07에서 답변을 받는다. 간격·응답 불명 복구·재시작 횟수 보존도 미정이며 임의 기대값으로 테스트하지 않는다.

### AC-05-11 — 승인 응답과 웹훅의 공통 검증·중복 보호
- **GIVEN** 카드 결제의 PAYMENT_STATUS_CHANGED 알림과 서버 결제 조회로 검증한 결과가 있다. 이번 테스트에서는 외부 조회 결과를 로컬 fixture로 전달한다.
- **WHEN** 같은 결제의 승인 응답·웹훅을 각각 먼저 처리하거나 같은 웹훅을 반복 처리한다.
- **THEN** 주문·금액·통화·카드·DONE·점유 기한 검증을 동일하게 적용하여 결제 반영 3,000원·예약 1건을 유지한다. 늦은 승인이라면 예약 0건·전액 환불 요청 1건을 유지한다. 검증 결과 없이 웹훅 본문의 DONE만으로 확정하지 않는다. 이미 처리한 결제는 늦게 재전달됐다는 이유로 새 환불을 만들지 않는다.
- **검증 범위:** 순수 규칙 테스트는 전달된 검증 결과의 판정·중복 보호만 확인한다. 웹훅 HTTP 수신, 실제 결제 조회, 응답 코드·재전송은 별도 통합 검증이며 이번 통과로 간주하지 않는다. PAYMENT_STATUS_CHANGED에 지급대행용 서명이 있다는 가정은 사용하지 않는다.

## US-06 — 내 예약 조회

### AC-06-1 — 예약과 결제 상태 구분
- **GIVEN** 로그인한 운전자에게 예약 또는 임시 점유가 있다.
- **WHEN** 내 예약 화면을 연다.
- **THEN** 충전소·충전기·원래 시작·종료·현재 예약 상태·체크인 기한·예약금 `3,000원`과 결제·환불 상태를 표시한다. 결제 대기, 확정, 체크인, 종료, 사용자 취소, 운영자 취소, 노쇼를 구분한다.

### AC-06-2 — 화면 내 결과 안내
- **GIVEN** 예약·취소·노쇼·환불·승계 결과가 발생했다.
- **WHEN** 사용자가 해당 화면을 조회한다.
- **THEN** 현재 결과와 금액을 확인할 수 있다. 문자·이메일·외부 푸시 발송을 요구하지 않는다.

## US-07 — 사용자 취소와 환불

### AC-07-1 — 2시간 이전 및 정확히 2시간
- **GIVEN** 원래 시작이 `2026-10-06 14:00:00`이고 예약금 `3,000원` 결제가 완료된 예약이다.
- **WHEN** 사용자가 `11:59:59` 또는 정확히 `12:00:00`에 취소한다.
- **THEN** 사용자 취소로 기록하고 `3,000원`을 전액 환불한다. 정확히 시작 `120분` 전을 전액 구간에 포함한다.

### AC-07-2 — 2시간 미만부터 정확히 30분
- **GIVEN** 원래 시작이 `2026-10-06 14:00:00`인 결제 완료 예약이다.
- **WHEN** `12:00:01`, `13:29:59` 또는 정확히 `13:30:00`에 취소한다.
- **THEN** `1,500원`을 환불하고 `1,500원`은 반환하지 않는다. `30분 ≤ 시작까지 남은 시간 < 120분`에 적용한다.

### AC-07-3 — 30분 미만과 시작 후
- **GIVEN** 원래 시작이 `2026-10-06 14:00:00`인 결제 완료 예약이다.
- **WHEN** 노쇼·종료 처리 전 `13:30:01`, `14:00:00` 또는 `14:05:00`에 사용자 취소한다.
- **THEN** 환불 금액은 `0원`이고 예약을 취소한다. 시작 후 취소도 `0원`이다.

### AC-07-4 — 취소 중복 방지
- **GIVEN** 같은 예약을 취소하여 환불 `1,500원`을 처리했다.
- **WHEN** 취소 요청이나 환불 성공 결과가 반복된다.
- **THEN** 누적 환불은 `1,500원`으로 유지하고 추가 환불·대기자 중복 승계를 만들지 않는다.

### AC-07-5 — 승계 예약 취소 기준
- **GIVEN** 원래 시작이 `14:00:00`이고 `14:20:00`에 결제 확정된 승계 예약이다.
- **WHEN** `14:21:00`에 사용자가 취소한다.
- **THEN** 확정 시각이 아닌 원래 시작 `14:00:00`을 기준으로 환불 `0원`을 적용한다.

## US-08 — 체크인

### AC-08-1 — 일반 예약 조기 체크인 경계
- **GIVEN** 시작 `14:00:00`, 종료 `15:00:00`인 일반 확정 예약이다.
- **WHEN** 체크인을 시도한다.
- **THEN** `13:49:59`에는 거절하고 정확히 `13:50:00`부터 허용한다. 시작 `10분` 전은 포함한다.

### AC-08-2 — 일반 예약 15분 경계
- **GIVEN** 시작 `14:00:00`인 일반 예약이며 아직 체크인하지 않았다.
- **WHEN** 체크인을 시도한다.
- **THEN** `14:14:59`에는 허용한다. 정확히 `14:15:00`에는 체크인을 거절하고 노쇼 취소, 환불 `0원`으로 처리한다. 허용 구간은 `[13:50:00, 14:15:00)`이다.

### AC-08-3 — 유효 예약과 중복 체크인
- **GIVEN** 자신의 확정 예약이 아니거나 이미 취소·노쇼·종료된 예약이다.
- **WHEN** 체크인을 시도한다.
- **THEN** 허용하지 않는다. 유효 예약의 체크인을 반복해도 체크인 실적은 1건이고 체크인만으로 예약금 `3,000원`을 반환하지 않는다.

### AC-08-4 — 시작 후 승계 체크인 기한
- **GIVEN** 원래 시작 `14:00:00`, 종료 `15:30:00`인 예약을 `14:20:00`에 승계 결제 확정했고 아직 체크인하지 않았다.
- **WHEN** 체크인을 시도한다.
- **THEN** `14:34:59`에는 허용하고 정확히 `14:35:00`에는 노쇼 처리한다. 원래 시작 + `15분`이 아니라 승계 확정 + `15분`을 적용한다.

### AC-08-5 — 미래 승계의 체크인 구간 (C-02 확정, 2026-10-11 사용자 답변)
- **GIVEN** 다음 날 `14:00:00` 시작 예약이 오늘 `10:00:00`에 승계 확정되었다.
- **WHEN** 체크인 기한을 계산하고 미체크인 예약의 노쇼 여부를 판정한다.
- **THEN** 원래 시작을 기준으로 다음 날 `[13:50:00, 14:15:00)`에 체크인한다. 오늘 `10:15:00`에는 노쇼로 취소하지 않고 다음 날 `14:14:59.999`까지 유지한다. 정확히 다음 날 `14:15:00`에는 노쇼 취소·환불 `0원`·진행 제한 해제로 처리한다. 시작 후 승계는 AC-08-4의 확정 +15분을 유지한다.

## US-09 — 이용 종료와 예약금 반환

### AC-09-1 — 수동 종료
- **GIVEN** 예약금 `3,000원` 결제를 완료하고 체크인한 진행 중 예약이다.
- **WHEN** 운전자가 이용 종료 버튼을 누른다.
- **THEN** 이용 종료로 기록하고 예약금 `3,000원` 전액 환불을 처리한다. 진행 중 예약 수에서 제외한다.

### AC-09-2 — 자동 종료 경계
- **GIVEN** 종료 `15:00:00`인 체크인 예약이며 종료 버튼을 누르지 않았다.
- **WHEN** 시연용 시계가 진행된다.
- **THEN** `14:59:59`에는 자동 종료하지 않고, 정확히 `15:00:00`에 자동 종료와 `3,000원` 전액 환불을 처리한다.

### AC-09-3 — 노쇼를 정상 종료로 반환하지 않음
- **GIVEN** 시작 `14:00:00`, 종료 `14:30:00`인 일반 예약이 미체크인으로 `14:15:00`에 노쇼 취소됐다.
- **WHEN** `14:30:00`에 도달한다.
- **THEN** 정상 이용 종료로 바꾸지 않고 환불 `0원`을 유지한다.

### AC-09-4 — 종료·환불 중복 방지
- **GIVEN** 수동 종료 후 `3,000원` 환불을 처리했다.
- **WHEN** 같은 예약의 종료 요청, 종료 시각 자동 처리 또는 환불 결과가 반복된다.
- **THEN** 종료 기록과 전액 환불은 각 1회만 반영하고 누적 환불이 `3,000원`을 초과하지 않는다.

## US-10 — 대기 신청

### AC-10-1 — 정확히 같은 구간에 대기
- **GIVEN** 충전기 A의 `14:00:00~15:00:00` 확정 예약이 있다.
- **WHEN** 운전자가 대기 신청한다.
- **THEN** A의 같은 시작 `14:00:00`·종료 `15:00:00` 예약에만 연결한다. A의 `14:30:00~15:30:00`이나 충전기 B의 `14:00:00~15:00:00`을 같은 대기열로 취급하지 않는다.

### AC-10-2 — 대기 1건과 무결제
- **GIVEN** 운전자에게 진행 중 예약 1건이 있고 대기는 없다.
- **WHEN** 다른 예약에 대기 신청한다.
- **THEN** 대기 1건을 허용하며 청구 금액은 `0원`이다. 이미 대기 1건이 있으면 두 번째 대기는 거절한다.

### AC-10-3 — 신청 시각 순서
- **GIVEN** 같은 대기열에 B가 `10:00:00`, C가 `10:00:01`에 신청했다.
- **WHEN** 대기 순서를 조회한다.
- **THEN** B가 1번, C가 2번이다. 신청 시각이 같은 경우의 보조 순서는 PRD 열린 질문 6에서 확정한다.

## US-11 — 결제 요청과 대기 승계

### AC-11-1 — 사용자 취소로 첫 대기자에게 요청
- **GIVEN** 원래 시작 `14:00:00`, 종료 `15:30:00` 예약에 B·C가 순서대로 대기하고 모두 진행 중 예약이 없다.
- **WHEN** 원래 예약자가 `14:05:00`에 사용자 취소한다.
- **THEN** B에게 예약금 `3,000원` 결제 요청을 화면에 표시하고 C에게 동시에 확정하지 않는다. B는 아직 확정 예약자가 아니며 결제 기한은 `14:15:00`이다.

### AC-11-2 — 10분 내 승계 결제
- **GIVEN** B에게 `14:05:00`에 결제 요청했으며 원래 종료는 `15:30:00`이고 B에게 진행 중 예약이 없다.
- **WHEN** `14:14:59`에 `3,000원` 승인과 자리 확보를 확인한다.
- **THEN** B의 승계 예약을 확정하고 종료는 `15:30:00`으로 유지한다. 원래 시작 시각은 취소 환불과 대기열 식별을 위해 보존한다.

### AC-11-3 — 결제 요청 정확히 10분 만료
- **GIVEN** B에게 `14:05:00`에 요청했고 B는 미결제이며 C가 다음 대기자다.
- **WHEN** 정확히 `14:15:00`에 도달하고 C에게 제공할 잔여시간이 충분하다.
- **THEN** B의 결제 기회를 만료하고 C에게 결제를 요청한다. C의 새 기한은 `14:25:00`이다. B의 기회는 `14:14:59.999`까지 유효하고 `14:15:00.000`부터 만료다. 정확히 만료 또는 이후에 처음 확인한 B의 카드·KRW·3,000원 DONE 승인은 승계 없이 전액 환불한다. 반복 이벤트로 다음 결제 요청·환불을 중복 생성하지 않는다. 2026-10-11 사용자 답변으로 확정했다.

### AC-11-4 — 노쇼 후 잔여 30분 경계
- **GIVEN** 원래 시작 `14:00:00`인 예약이 `14:15:00`에 노쇼 처리됐다.
- **WHEN** 승계 기회를 판단한다.
- **THEN** 종료가 `14:30:00`이면 잔여 `15분`이므로 승계하지 않는다. 종료가 `15:00:00`이면 잔여 `45분`이므로 첫 대기자에게 결제를 요청한다. 잔여가 정확히 `30분`이면 최소 잔여시간 조건을 통과하고 `29분 59초`면 통과하지 않는다.

### AC-11-5 — 종료 시각 유지
- **GIVEN** 시작 `14:00:00`, 종료 `15:00:00` 예약의 노쇼 후 B가 `14:20:00`에 승계 확정했다.
- **WHEN** B가 체크인하여 이용한다.
- **THEN** 남은 `40분`을 이용하며 종료는 `15:00:00`이다. 다음 예약을 밀어내어 `15:20:00`까지 연장하지 않는다.

### AC-11-6 — 승계자 재노쇼
- **GIVEN** 원래 종료 `15:30:00`, B의 승계 확정 `14:20:00`, B의 체크인 기한 `14:35:00`, 다음 대기자 C가 있다.
- **WHEN** B가 미체크인인 채 정확히 `14:35:00`에 도달한다.
- **THEN** B를 노쇼 취소하고 환불 `0원`을 적용한다. 잔여 `55분`이므로 C에게 결제를 요청하고 원래 종료 `15:30:00`을 유지한다.

### AC-11-7 — 노쇼 승계의 승인 시 잔여시간 재검사
- **GIVEN** 노쇼 예약의 원래 종료가 `15:00:00`이고 C에게 `14:25:00`에 요청하여 결제 기한은 `14:35:00`이다.
- **WHEN** 결제 기한 전 C의 카드·KRW·3,000원 DONE 승인을 확인한다.
- **THEN** 요청과 승인 확인 시 모두 잔여시간이 30분 이상이어야 승계한다. `14:29:59.999`와 정확히 `14:30:00.000`에는 다른 조건이 유효하면 확정하고 원래 종료를 보존한다. `14:30:00.001`, `14:30:01`에는 결제 기한 전이어도 승계하지 않고 3,000원 전액 환불을 요청한다. 동일 승인 반복으로 추가 환불하지 않는다. `14:35:00` 승인은 잔여 미달이며 AC-11-3의 기한 만료에도 해당하므로 승계 없이 전액 환불 1건이다. 2026-10-11 사용자 답변으로 확정했다. 사용자 취소 승계에도 최소 잔여시간을 적용할지는 C-01에 미정으로 남긴다.

### AC-11-8 — 예약 보유 대기자 [조건부]
- **GIVEN** 첫 대기자 B가 진행 중 예약 1건을 이미 가지고 있다.
- **WHEN** B의 승계 차례가 된다.
- **THEN** 진행 중 예약을 2건으로 확정하지 않는다. B 건너뛰기·보류 여부는 PRD 열린 질문 3에서 확정한다.

## US-12 — 운영자 취소 안내

### AC-12-1 — 운영자 취소 전액 환불
- **GIVEN** 예약금 `3,000원` 결제가 완료된 예약이다.
- **WHEN** 운영자가 점검·고장 사유로 취소한다.
- **THEN** 원래 시작까지 남은 시간이 `120분`, `30분`, `0분`이거나 시작 후 `5분`이더라도 `3,000원` 전액 환불한다. 사용자 취소의 부분·무환불 규칙을 적용하지 않는다.

### AC-12-2 — 예약·대기 취소 안내
- **GIVEN** 운영자 취소된 예약과 그 예약에 연결된 대기 신청이 있다.
- **WHEN** 예약자·대기자가 자신의 화면을 조회한다.
- **THEN** 운영자 취소 사유와 예약자의 `3,000원` 환불 상태를 표시한다. 대기는 취소되고 결제 요청·승계를 하지 않으며 무결제 대기자에게 환불할 금액은 `0원`이다.

## US-13 — 운영자 예약 목록

### AC-13-1 — 담당 충전소 예약 조회
- **GIVEN** 운영자 계정 1개에 충전소 1곳이 지정되어 있다.
- **WHEN** 예약 목록을 조회한다.
- **THEN** 담당 충전소의 충전기·예약자 테스트 계정·시간·예약 상태·체크인·노쇼·결제·환불 상태를 확인할 수 있다.

### AC-13-2 — 담당 외 권한 차단
- **GIVEN** 담당 충전소 외의 충전소가 서울 원본 데이터에 있다.
- **WHEN** 운영자가 해당 충전소의 예약 관리·점검 차단·해제·취소를 시도한다.
- **THEN** 관리 권한을 거절한다. 일반 충전소 정보 조회와 운영자 관리 권한을 구분한다.

## US-14 — 점검 차단과 해제

### AC-14-1 — 신규 예약 차단
- **GIVEN** 담당 충전기가 원본상 예약 가능한 상태이고 향후 확정 예약이 있다.
- **WHEN** 운영자가 점검 차단한다.
- **THEN** 신규 예약·확정을 막되 기존 확정 예약은 자동 취소·환불하지 않는다. 기존 예약을 목록에 유지하여 개별 취소할 수 있게 한다.

### AC-14-2 — 운영자 차단 해제
- **GIVEN** 원본의 예약 자격을 만족하는 충전기에 운영자 차단만 설정되어 있다.
- **WHEN** 담당 운영자가 차단을 해제한다.
- **THEN** 운영자 차단을 제거하고 충돌 없는 예약을 다시 허용한다.

### AC-14-3 — 원본 제한 유지
- **GIVEN** 원본·상태 변경분의 유효 상태가 고장·점검(`4/5`) 또는 상태 확인 불가이고 운영자 차단도 있다.
- **WHEN** 운영자가 자신의 차단을 해제한다.
- **THEN** 원본 제한은 유지하고 예약을 계속 막는다. 이용 제한·삭제·24시간 조건도 우회하지 않는다.

## US-15 — 운영자의 개별 취소

### AC-15-1 — 개별 취소와 대기열 종료
- **GIVEN** 담당 충전기의 예약 A·B가 있고 A에 대기 신청이 있다.
- **WHEN** 운영자가 점검 사유로 A만 취소한다.
- **THEN** A만 운영자 취소로 기록하고 A의 예약금 `3,000원`을 전액 환불하며 A의 대기도 함께 취소한다. B는 그대로 유지하고 A의 대기자에게 승계하지 않는다.

### AC-15-2 — 중복 취소·환불 방지
- **GIVEN** 운영자 취소로 `3,000원` 전액 환불한 예약이다.
- **WHEN** 동일 취소나 환불 결과를 재처리한다.
- **THEN** 누적 환불을 `3,000원`으로 유지하고 대기 취소·화면 상태를 중복 생성하지 않는다.

## US-16 — 자동 노쇼 처리

### AC-16-1 — 일반 노쇼 정확한 기한
- **GIVEN** 시작 `14:00:00`인 일반 예약이 아직 미체크인이다.
- **WHEN** 시연용 시계가 진행된다.
- **THEN** `14:14:59`에는 노쇼가 아니고 정확히 `14:15:00`에 노쇼 취소, 환불 `0원`, 진행 중 예약 제한 해제를 처리한다.

### AC-16-2 — 체크인한 예약 보호
- **GIVEN** 시작 `14:00:00` 예약이 `14:14:59`에 체크인 완료됐다.
- **WHEN** 시계가 `14:15:00`을 지난다.
- **THEN** 노쇼로 취소하지 않으며 종료 시각 또는 이용 종료 버튼까지 체크인 상태를 유지한다.

### AC-16-3 — 노쇼 승계와 중복 방지
- **GIVEN** 노쇼 예약에 유효 대기자가 있고 잔여시간이 `30분` 이상이다.
- **WHEN** 노쇼 기한 이벤트를 2회 이상 처리한다.
- **THEN** 노쇼 기록 1건, 환불 `0원`, 첫 대기자의 활성 결제 요청 1건만 유지한다. 잔여시간이 `30분` 미만이면 승계 요청하지 않는다.

## US-17 — 시연용 시계와 성공 지표

### AC-17-1 — 시계로 예약 종료 시연
- **GIVEN** 체크인한 예약의 종료가 `15:00:00`이고 시계는 `14:59:59`이다.
- **WHEN** 시연용 시계를 `1초` 진행한다.
- **THEN** 자동 종료·`3,000원` 환불을 처리하고 화면의 예약 시각·상태를 서울 시간으로 표시한다. 실제 컴퓨터 시간을 바꿀 필요가 없어야 한다.

### AC-17-2 — 시계로 노쇼·대기 기한 시연
- **GIVEN** 시작 `14:00:00`, 종료 `15:30:00`의 미체크인 예약과 대기자 B·C가 있으며 시계가 `14:14:59`이다.
- **WHEN** 시계를 `14:15:00`, 이어서 `14:25:00`까지 진행하고 B는 미결제이다.
- **THEN** `14:15:00`에 원래 예약을 노쇼 처리하고 B에게 결제 요청한다. 정확히 `14:25:00`에는 B의 기회를 만료하고 C에게 요청한다. 이벤트는 시간 순서대로 처리하고 같은 노쇼를 반복 집계하지 않는다.

### AC-17-3 — 체크인 기준 지표
- **GIVEN** 판정 완료 예약 10건 중 체크인 6건, 노쇼 2건, 사용자 취소 1건, 운영자 취소 1건이 있고 체크인 6건에는 이후 취소가 없다.
- **WHEN** 지표를 조회한다.
- **THEN** 평가 분모는 `8건`, 예약 이행률은 `6 ÷ 8 × 100 = 75%`, 노쇼율은 `2 ÷ 8 × 100 = 25%`이다. 체크인한 6건의 종료 여부는 이행 판정에 영향을 주지 않는다. 목표 달성·미달 표시를 하지 않는다.

### AC-17-4 — 노쇼 취소를 취소 제외하지 않음
- **GIVEN** 노쇼 1건이 자동으로 취소 상태가 됐고 사용자 취소 1건과 운영자 취소 1건이 별도로 있다.
- **WHEN** 지표를 산출한다.
- **THEN** 노쇼 1건은 분모·노쇼 분자에 포함하고 사용자·운영자 취소 2건만 제외한다. 이 표본의 이행률은 `0%`, 노쇼율은 `100%`이다.

### AC-17-5 — 미확정·판정 대기 제외 [조건부]
- **GIVEN** 결제 대기·임시 점유·대기 신청과 아직 기한 전인 미체크인 예약만 있다.
- **WHEN** 지표를 조회한다.
- **THEN** 평가 분모를 `0건`으로 보고 `집계 대상 없음`을 표시하는 초안 해석을 적용한다. 분모 `0`으로 나누거나 이행률 `100%`를 만들지 않는다. 판정 대기 제외와 표시 방식은 PRD 열린 질문 7에서 확인한다.

### AC-17-6 — 승계·체크인 후 취소 집계 [조건부]
- **GIVEN** 원래 예약 노쇼 1건, 별도 승계 예약 체크인 1건, 체크인 후 사용자 취소 1건이 있다.
- **WHEN** 지표를 산출한다.
- **THEN** 승계 예약을 별도 1건으로 포함하고 체크인 후 사용자 취소는 분자·분모에서 함께 제외하는 초안 해석이라면 분모 `2건`, 이행률 `50%`, 노쇼율 `50%`이다. 이 해석은 PRD 열린 질문 7에서 확인한다.

## US-18 — MCP 예약 보조 (2026-10-12 사용자 요청)

### AC-18-1 — 도구 세 개와 기존 제한
- **GIVEN** 운전자가 검색·임시 점유·결제 링크 요청 흐름을 이용한다.
- **WHEN** MCP 도구를 제공한다.
- **THEN** 충전기 검색, 10분 임시 점유, 결제 링크 요청을 각각 제공하며 기존 커넥터·자격·시간·겹침·권한 제한을 유지한다. 순수 규칙 테스트는 검색 후보 판정·기한 계산 부분만 검증하며 도구 등록·원자적 저장까지 검증하지 않는다.

### AC-18-2 — 인간 승인 없는 링크 생성 금지
- **GIVEN** 사람의 결제 링크 생성 승인이 확인되지 않았다.
- **WHEN** 결제 링크를 요청하거나 모델이 도구 인수에 `approved: true` 같은 승인을 주장한다.
- **THEN** 결제 링크·생성 효과를 만들지 않고 해당 점유·예약 구간·예약금 3,000원(KRW)·만료 요약과 `npm run approve -- <holdId>` 명령을 반환한다. 모델의 승인 주장은 승인 파일 존재를 대신하지 않는다. 명령 실제 동작은 별도 통합 검증이다.

### AC-18-3 — 오늘 저녁 7시 정규화
- **GIVEN** 시연용 현재 시각과 `강남역 근처 DC콤보 충전기 7시에 30분 예약해 줘` 요청이 있다.
- **WHEN** 예약 시간을 정규화한다.
- **THEN** 서울 시연용 시계의 오늘 `19:00:00~19:30:00`으로 해석한다. 오늘 19시가 현재보다 과거면 기간 조건을 통과하지 않으며 내일로 바꾸지 않는다. 다른 문장 해석은 C-13에서 확인한다.

### AC-18-4 — 반경 1km 검색
- **GIVEN** 강남역 기준 후보 거리와 선택 커넥터 DC콤보가 있다.
- **WHEN** 검색 후보를 판정한다.
- **THEN** 반경1km 이하의 기존 예약 조건을 만족하는 후보만 제공한다. `999m`와 정확히`1000m` 포함, `1001m` 제외이며 거리 오름차순·동률은statId/chgerId 순서다(추가 사용자 답변). 이번 서버의 운영시간은 정확히 `24시간 이용가능`만 허용한다. 기존 순수 테스트의 별도 갱신과 재확인이 필요하다.

### AC-18-5 — 점유 만료 후 링크 사용 금지
- **GIVEN** 임시 점유의 만료가 `10:10:00.000`이다.
- **WHEN** 결제 링크의 유효 여부를 확인한다.
- **THEN** 링크 기한은 점유 기한 이하이고 정확히 `10:10:00.000` 및 이후에는 사용할 수 없다. 만료 전이어도 사람 승인 없는 생성은 AC-18-2에 따라 금지한다. 점유 생성 시점·링크 재요청은 C-14에서 별도 확인한다.

### AC-18-6 — 인증·승인 파일·도구 통합 [조건부]
- **GIVEN** 실제 MCP 호출에서 로그인 사용자·점유 소유자·승인 증거를 확인해야 한다.
- **WHEN** 승인 후 링크 생성과 중복 요청을 처리한다.
- **THEN** C-14·C-15의 남은 파일 경로/규약·인증·중복·복구 답변 후 통합 기준을 추가한다. AC-18-7의 파일 존재와 점유 기한에 관한 순수 성공 판정은 확정됐지만 실제 파일 생성·가드 보호·MCP 연결은 별도 검증이다. 모델이 전달한 boolean은 파일 존재 근거가 아니다.

### AC-18-7 — 터미널 승인 파일과 유효 점유
- **GIVEN** 사용자가 터미널에서 `npm run approve -- <holdId>`를 실행해 해당 점유의 승인 파일을 생성하는 흐름이다. 승인 폴더는 사용자 가드로 보호한다.
- **WHEN** 결제 링크 요청을 판정한다.
- **THEN** 해당 holdId의 승인 파일이 존재하고 점유 기한 미만일 때만 링크 생성이 가능하다. 파일이 없거나 다른 점유의 승인이거나 정확히 만료 및 이후면 링크 생성 효과는 없다. 순수 테스트는 adapter가 제공한 신뢰된 파일 존재·대상 snapshot으로 판정만 검증하고 실제 파일·명령·가드 동작을 대신하지 않는다.

### AC-18-8 — 실제 stdio MCP 도구 등록과 호출
- **GIVEN** 합의한 공식SDKv2.3.1 stdio 서버와 로컬 설정이다.
- **WHEN** SDK Client가 초기화하고 tools/list·tools/call을 수행한다.
- **THEN** search_chargers·hold_charger·request_payment_link 세 도구를 발견하고 호출할 수 있다. 도구 입력의 승인 주장·저장root·사용자·시계는 신뢰된 서버 context를 대신하지 않는다. stdout은 프로토콜에만 사용한다.

### AC-18-9 — 실제 터미널 승인 명령과 파일 읽기
- **GIVEN** 유효 점유가 있고 승인 파일은 없다.
- **WHEN** 사람이 `npm run approve -- <holdId>`를 실행한 후 서버가 링크를 요청받는다.
- **THEN** `.codex/approvals/<holdId>.json`에 해당 점유 승인을 저장하고 서버가 파일을 읽어 판정한다. 에이전트는 실제 승인 폴더에 쓰지 않는다. 자동 테스트는 격리 임시root의 실제 파일I/O만 검증하며 실제 인간 명령 실행은 사용자의 시연으로 구분한다.
- **만료경계:** approve확인시각이 점유만료이상이면오류로거절하고 새승인파일을생성하지않는다.

### AC-18-10 — 독립 점유·원자적 저장·기한 유지
- **GIVEN** 예약 가능한 충전기·시간에 요청이 들어온다.
- **WHEN** hold 생성과 겹치는 동시 요청을 저장한다.
- **THEN** 생성부터정확히10분의 점유를 저장하고 같은 충전기 겹치는 유효 점유를 중복 확보하지 않는다. 승인·링크 요청·같은 요청 반복으로 원래 기한을 연장하지 않는다. 재요청 식별 계약은 서버 계획에 따른다.
- **재요청:** 동일requestId/동일payload는기존hold반환·기한유지, 다른requestId의겹치는유효hold는거절한다. 같은키다른payload는키충돌이다. 만료후새requestId는기존자격/시간조건을충족할때만신규hold를생성한다.
- **직접hold:** 선택connector를 필수로 받고 저장/payload에 보존한다. 검색 없이 직접호출해도 AC-02-6·7·8의 커넥터지원과 기존자격을 재검사한다. 계정별선택저장·변경(C-11)은 미정으로 유지한다.

### AC-18-11 — 결제 없는 링크 주소
- **GIVEN** 해당 점유의 승인 파일이 존재하고 점유가 유효하다.
- **WHEN** 결제 링크 도구를 호출한다.
- **THEN** 결제 없는 링크 주소와 점유 기한 이하의 만료를 반환한다. 미승인 시에는 기존요약·명령만, 정확히만료와이후에는 새 주소 생성 없이 거절한다. HTTP 페이지·토스결제·실제주소사용 차단은 이번검증에 포함하지 않는다.

#### 후속 HTTP 연결의 확인 부분 (T-58, 2026-10-12 사용자 요청)

위 제외 범위는 기존 T-54~57의 주소 생성 검증에 관한 기록이다. 후속 T-58은 다음 부분을 별도로 검증한다.

- 승인 파일과 유효 점유의 반환 주소를 열면 기존 5180 시연 서버에서 그 점유의 주문을 표시한다.
  충전기·선택 커넥터·시작/종료·원래 생성/만료와 예약금3,000원/KRW를 유지하며 조회로 기한을 늘리지 않는다.
- AC-18-2·5·7, AC-03-4에 따라 페이지와 주문 API 모두 미승인·잘못된 승인·만료·타인·없는 점유를 거절한다.
  결제 위젯/버튼 대신 코드와 해당 한국어 이유를 안내한다.
- 결제 직전 조회 게이트를 재검사한다. 반복·동시·재시작 조회에도 같은 주문1건과 원래 만료를 유지한다.
- 연결로 인한 결제 완료는 없으며 AC-05-6을 유지한다. 성공/실패/결과는 같은 주문의 기존 승인 규칙으로 연결한다.
  실제 토스 승인·환불 완료는 별도이며 로컬 HTTP·위젯 렌더링 확인으로 대신하지 않는다.
- 사용자 확인된 `tests/mcp/payment-page.test.ts`12개와 브라우저 확인 범위·미검증 사항은
  [연결 검증 기록](mcp-payment-page-validation.md)에 구분해 기록한다.

### AC-18-12 — Codex 접속 예제와 격리 검증
- **GIVEN** 로컬서버 시작명령과 신뢰된 환경설정이다.
- **WHEN** Codex접속예제와 검증결과를 제공한다.
- **THEN** 전역설정 자동수정 없이 stdio 등록예제를 제공한다. 임시root의 CLI/MCP 파일I/O, 실제Codex등록, 인간승인파일생성을 서로 구분해 보고한다.

### AC-18-13 — 명시 날짜·시작 시각 검색
- **GIVEN** 서울 시연용 현재 시각이 `2026-10-12 10:00:00`이고 강남역/DC콤보의 검색 조건이 있다.
- **WHEN** `date:'2026-10-13'`, `startTime:'15:00'`, `durationMinutes:30`으로 검색한다.
- **THEN** 서울 `2026-10-13 15:00:00~15:30:00`의 정확한 epoch 구간을 반환한다.
  같은 날짜의 `19:00`은 `19:00~19:30`이며 오늘19시로 바꾸지 않는다. 길이60·90분도 보존한다.
  서울 자정은 UTC 전날이어도 요청한 서울 날짜로 해석하고, 유효 윤년·월말·연말 구간은 정확히 변환한다.
  날짜 정규화는 호스트 시간대에 의존하지 않는다. 2026-10-12 사용자 답변으로 확정했다.

### AC-18-14 — 입력 방식 독립과 잘못된 날짜·시각 거절
- **GIVEN** 명시 `date:YYYY-MM-DD`/`startTime:HH:mm` 한 쌍 또는 기존 `timeText:'7시'` 단독 계약이다.
- **WHEN** 두 방식을 혼용하거나 날짜/시각 한 필드 누락, 시간 입력 없음, 잘못된 달력 날짜·시각·형식을 전달한다.
- **THEN** `INVALID_ARGUMENTS`로 거절하고 검색 후보·점유·링크·결제 효과를 만들지 않는다.
  `2026-02-29`, `2026-02-30`, `2026-13-01`, `2026-1-02`, 공백·빈 문자열,
  `24:00`, `19:60`, `7:00`, 초·오프셋을 첨부한 시각을 자동 보정하여 허용하지 않는다.
  기존7시 단독 입력은 AC-18-3을 유지하며 과거 오늘19시를 내일로 바꾸지 않는다.
  오류 코드는 기존 service의 내부 계약을 재사용한다. 2026-10-12 사용자 답변으로 입력 정책을 확정했다.

### AC-18-15 — 기존 시간 제한·MCP 연결·점유 구간 보존
- **GIVEN** 명시 날짜·시각과 신뢰된 서버 시연용 시계가 있다.
- **WHEN** 실제 SDK의 `tools/list`·`tools/call`로 검색하고 반환 구간을 기존 점유 도구에 전달한다.
- **THEN** 신규 날짜·시각 필드를 발견·호출할 수 있으며 AC-04-1·2의 현재~7일 포함 경계,
  00/30분 시작·30/60/90분 길이를 적용한다. 유효 날짜이지만 기간·시작 단위 위반은 `INVALID_TIME`이다.
  마지막 허용 시작의 종료가7일을 넘어도 허용하며 `nowMs`·사용자·승인·저장root 위조 입력은 수용하지 않는다.
  기존 자격·커넥터·겹침을 유지하고 점유에는 같은 시작/종료와 생성+10분 기한을 보존한다.
  SDK/점유 검증은 격리 root이며 실제 인간 승인·토스 완료를 대신하지 않는다.

## 남은 정책 결정과 검증 상태

- 조건부 기준과 PRD 열린 질문을 확정한 후 최종 수용 기준으로 전환한다.
- 앱 종료 중 시간 경과 복구, 시계 역행·초기화, 결제·환불 실패 재시도, 대기 철회 등은 열린 질문 해결 후 기준을 추가한다.
- 이번 MCP 테스트의 에이전트 직접 실행은 `NOT_RUN`이다. 이전 32개 버전은 Stop 훅이 실제 실행하여 함수 미구현으로 32개 `FAIL`, 기존 156개 `PASS`, 타입 검사 `PASS`를 보고했다. 새 승인 파일 계약의 수정 테스트는 아직 실행하지 않았다. 훅 실행 실패를 사용자 테스트 확인이나 구현 착수 승인으로 간주하지 않는다.
