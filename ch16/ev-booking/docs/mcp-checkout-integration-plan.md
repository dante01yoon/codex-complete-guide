# 16장 MCP 주문과 15장 결제 화면 연결 계획

상태: 사용자 확인 대기. 기능 구현·신규 테스트 작성·결제 서버 재시작은 아직 수행하지 않았다.

## 현재 확인한 연결 단절

- `src/mcp/stdio.ts`의 점유 저장소는 프로세스 메모리이다. 공유 점유 파일은 없다.
- `createPaymentLink`는 UUID URL만 반환한다. 주문번호와 holdId의 대응을 저장하지 않는다.
- `src/payments/demo-server.ts`는 별도의 demo-UUID 주문·가상 충전소·시간을 생성한다. MCP 주문을 조회하지 못한다.
- `.codex/approvals/<holdId>`만 실제 파일 계약이 있다. 결제 서버도 기존 lstat 기반 일반 파일 확인을 재사용하고 승인 파일을 쓰거나 삭제하지 않는다.
- 기존 자동 테스트 171/171 및 타입 검사 PASS. 신규 HTTP 연결의 사용자 테스트 확인·RED 증거는 없다.
- `.codex/TEST_WRITING` 파일이 없는 상태다. guard.sh는 신규 파일을 포함한 tests/ 쓰기를 사람의 테스트 작성 모드로 제한한다. 훅 차단을 실행한 것은 아니며 읽기 확인 근거다.

## 제안하는 연결

관련 범위: US-18·US-05·US-06, T-52·T-54 및 T-15의 연결 부분. 기존 AC-18-11의 URL 문자열 계약은 유지하면서 별도 checkout 수용 기준을 추가한다.

권장안은 MCP 런타임이 점유와 주문번호 대응을 원본과 분리된 로컬 공유 파일로 내보내고, 결제 서버가 요청마다 그 파일을 읽는 것이다. 사용자 요청의 파일 공유 방식에 부합한다. 대안인 MCP 조회 HTTP API는 파일 공유 요청과 다르고 별도 서버가 필요하다. 두 서버를 하나의 프로세스로 합치는 방식은 stdio MCP 실행 구성을 바꾼다.

- 저장할 정보: 주문번호, holdId, 시연 계정, 충전소·충전기 식별자, 선택 커넥터, 예약 시작·종료, 점유 생성·만료와 공통 시계 기준. 키·결제 인증값·승인 여부는 저장하지 않는다.
- 공유 파일 위치와 MCP 재시작 시 점유 복원 여부는 기존 C-10·C-09에서 확정되지 않았다. 제안은 로컬 런타임 전달용 파일이며 재시작 복원·기한 연장은 추가하지 않는 것이다. 파일 위치는 승인 폴더·원본 밖으로 정하고 버전 관리에서 제외한다.
- `/checkout/<orderId>`는 MCP가 발급한 주문만 조회한다. 실제 원본의 충전소명과 주문의 예약 시간을 서울 시간으로 표시하고 3,000원 테스트 위젯에 연결한다.
- 알 수 없는 주문·점유 정보 없음·사람 승인 없음·정확히 10분 만료·깨진 공유 파일은 사유 화면을 반환한다. 결제 SDK·결제 버튼을 제공하지 않는다. 승인 조회 뒤에도 만료를 재검사한다.
- 페이지를 연 후 결제 버튼을 누를 때도 서버에서 승인과 점유를 재검사한다. 열린 화면 때문에 기한을 연장하지 않는다.
- 기존 카드/DONE 확인·금액 대조·중복 방지·승인 후 만료 보상은 confirm.ts를 재사용한다. MCP 주문마다 해당 충전기와 구간을 사용하고 합성 주문의 전역 시간 정보를 사용하지 않는다.
- 실제 로그인 도입·MCP 영속 예약 확정·재시작 복구는 이번 화면 연결의 완료로 주장하지 않는다. MCP의 기존 확정 예약 기록과 결제 성공의 통합까지 필요하면 별도 범위를 확정한다.

## 신규 테스트 확인안

기존 tests/ 파일은 수정하지 않는다. 신규 파일 `tests/payments/mcp-checkout.test.ts`만 별도 테스트 작성 단계에서 추가할 계획이다. 실제 사람 승인 폴더는 건드리지 않고 승인 확인 어댑터를 모의한다. 공유 파일 I/O는 임시 디렉터리에서 검증한다. 아래 번호는 추가할 AC 제안이며 기존 AC를 변경하는 것은 아니다.

| AC 제안 / 정확한 테스트 이름 | 입력 | 기대 결과 |
|---|---|---|
| AC-18-13 MCP 링크의 주문번호로 같은 점유를 조회한다 | 런타임이 발급한 링크와 해당 점유 | 저장한 주문번호·holdId·충전기·예약 구간 일치, HTTP 조회가 새 점유를 생성하지 않음 |
| AC-18-13 승인된 유효 주문에 충전소와 서울 예약 시간과 3000원 위젯을 표시한다 | 승인 존재, 만료 1ms 전 | 실제 충전소명·서울 시작/종료·3000원·위젯 초기화 포함 |
| AC-18-14 승인 없는 주문은 이유만 표시한다 | 해당 승인 파일 없음 또는 다른 holdId 승인 | 승인 필요 안내, SDK·결제 버튼 없음, 승인 쓰기 0회 |
| AC-18-14 정확히 점유 만료 시각과 이후에는 위젯을 표시하지 않는다 | 생성+600000ms 및 +600001ms | 만료 안내, SDK·결제 버튼 없음, 기존 expiresMs 유지 |
| AC-18-14 승인 파일 확인 도중 만료되면 위젯을 표시하지 않는다 | 승인 조회 전 유효, 조회 후 만료 | 만료 안내, 위젯 없음 |
| AC-18-14 알 수 없는 주문과 손상된 점유 정보는 결제를 막는다 | 미등록 ID·유효하지 않은 파일 | 조회 불가 사유, 합성 주문 생성 없음, 위젯 없음 |
| AC-18-14 결제 직전에 승인 제거와 점유 만료를 재검사한다 | 열린 페이지 이후 승인 false 또는 만료 | 결제 시작 거절, 승인 API 호출 없음 |
| AC-18-13 두 주문은 각자의 충전소와 예약 시간을 표시한다 | 서로 다른 충전소·구간의 두 주문 | 주문별 정보 격리, 전역 합성 주문 값 사용 없음 |

사용자 확인 후 신규 테스트 작성 → 구체적인 작성 테스트 확인 → 실제 기능 RED → src 구현 → 전체 테스트·타입 검사·테스트 불변 확인 → 서버 재시작 → HTTP·브라우저 확인 순서로 진행한다. import 오류만으로 기능 RED를 보고하지 않는다.

## 완료 후 확인 방법

1. 새 MCP 런타임에서 search_chargers → hold_slot으로 유효한 점유를 만든다. 기존 메모리 점유와 주문번호는 재시작 시 복원된다고 가정하지 않는다.
2. 사람이 프로젝트 터미널에서 `npm run approve -- <holdId>`를 직접 실행한다.
3. request_payment가 반환한 URL을 10분 기한 안에 연다. 해당 충전소·예약 시간·3,000원·테스트 위젯을 확인한다.
4. 같은 링크를 만료 후 열어 사유 화면과 위젯 부재를 확인한다. 승인 제거 검증은 사람이 수행하며 코덱스는 승인 파일을 변경하지 않는다.
5. 최종 테스트 카드 인증·승인·환불은 실제 수행한 경우에만 PASS로 기록한다. 화면 렌더와 결제 완료를 구분한다.
