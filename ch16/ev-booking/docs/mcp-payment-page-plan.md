# MCP 결제 링크 → 15장 시연 서버 연결안

2026-10-12 사용자 요청. 관련 T-52·56·57, US-05·06·18,
AC-05-1·3·6·7·8, AC-06-2, AC-18-2·5·7·10·11의 HTTP 연결 부분.
기존 주소 생성·격리 MCP 검증 완료 근거는 `mcp-server-validation.md`이다.

## 연결 방식

기존 5180 Node HTTP 서버를 확장한다. MCP의 `/payment/<holdId>`를 그대로 사용하고
서버가 신뢰된 root·actor·시계로 저장 점유와 승인 파일을 읽는다.
승인 파일의 정규파일·대상 검사와 점유 판정은 기존 adapter/rules를 재사용한다.
미승인·만료·없는 점유·소유자 불일치는 결제 UI 대신 코드와 한국어 이유를 표시한다.
거절 화면에는 토스 SDK·결제 버튼을 넣지 않는다. 직접 API 호출에도 같은 검사를 적용한다.

페이지의 주문 조회는 `GET /api/payment/<holdId>`를 사용한다.
점유의 충전기·선택 커넥터·시작·종료·원래 생성/만료를 사용해 3,000원 KRW 주문을
기존 시연 주문 저장소에 한 번만 연결한다. 새로고침·동시 조회·서버 재시작도 같은 주문을 반환한다.
다른 충전소 자동 선택이나 새 10분 점유 생성으로 대체하지 않는다.
원본·점유 파일·승인 파일은 조회 과정에서 수정하지 않는다.
클라이언트가 금액·소유자·기한을 지정할 수 없다.

기존 `/` 단일 주문 시연은 유지하며 `/payment` 화면에서는 기본 주문 생성 API를 호출하지 않는다.
현재 HTML의 고정 60분·DC콤보 표시는 실제 점유 길이·커넥터로 바꾼다.
결제 클릭 직전에도 조회 게이트를 재검사한다. 성공/실패/결과 URL은 같은 주문으로 이어진다.
기존 승인·금액 검증·DONE 판정·늦은 승인 환불 규칙을 재사용한다.
이미 외부 카드 인증을 끝낸 승인 반환은 만료만으로 기존 보상 처리 경로를 건너뛰지 않는다.
새 예약·대기 정책이나 MCP 전체 예약 저장 모델 확장은 이번 주문 표시 작업의 완료로 주장하지 않는다.

기본 MCP 링크 포트 5181은 시연 서버 5180과 일치시키는 내부 연결 변경이다.
명시적인 `EV_BOOKING_LINK_BASE_URL` 설정은 유지한다. 전역 Codex 설정은 자동 수정하지 않는다.

## 다른 접근의 검토

- 별도 HTTP 서버: 중복된 주문·토스·결과 경로가 필요해 기존 시연과 어긋날 위험이 있다.
- 브라우저에서 점유를 새 주문으로 복사: 원래 기한·승인·소유자 검사를 서버에서 보장하기 어렵다.
- 권장안: 기존 시연 서버의 HTTP 경로와 주문 adapter를 확장한다.

## 테스트 계약과 진행 관문

`tests/mcp/payment-page.test.ts`는 실제 루프백 HTTP와 격리 임시 root만 사용한다.
새 공개 진입점 `src/demo/payment-server.ts`의 `createPaymentDemoServer(options)`는
listen 전 Node Server를 반환한다. options는 기존 BookingOptions와 테스트 clientKey,
주입 가능한 `toss` 호출 adapter이며 HTTP·모델 인수로 노출하지 않는다.
실행 entry `src/demo/server.ts`가 실제 .env 테스트 키·5180 listen을 담당한다.
factory import 자체는 환경 파일 조회·서버 시작·실제 토스 호출을 하지 않는다.
테스트는 기존 테스트 설정에 이미 포함되는 mcp 경로에 두며 설정은 바꾸지 않는다.

검증: 승인+유효 점유 주문 연결, 원래 기한·선택값·금액 유지,
동시/반복/재시작 조회 멱등성, 미승인과 잘못된 승인, 만료 직전/정확히/직후,
승인 제거 후 API 거절, 타인·없는 점유, 외부 토스 호출 없음.
브라우저의 실제 요약·길이·커넥터·위젯과 거절 이유는 구현 후 별도 확인한다.

사용자 테스트 확인 → 실제 Red → 구현(테스트 불변) → Green·타입 검사 → 브라우저 확인.
기존 T-52 화면 검증 예외를 새 MCP HTTP 기능 테스트 확인의 자동 면제로 해석하지 않는다.
실제 승인 폴더 쓰기·approve 실행·토스 승인/환불·배포는 수행하지 않는다.

거절 페이지는 HTML의 코드·한국어 사유를 확인하고 토스 SDK·위젯/결제 버튼이 없음을 검증한다.
모든 사례에서 주입한 toss adapter 호출0회를 확인한다.
임시 root에서만 실제 점유/승인 fixture·주문 파일I/O와 루프백 HTTP를 사용하는 계약이다.
NACS/30분 요약이 실제 화면에 렌더링되는지, 기본 5180 연결과 클릭 직전 재검사,
성공·실패·결과 이동은 구현 후 브라우저 확인 대상이다. 이번12개로 브라우저/실결제 통과를 주장하지 않는다.
AC-05-7·8의 기존 승인 규칙은 이번 테스트에서 새로 변경하거나 실연결 검증하지 않는다.
