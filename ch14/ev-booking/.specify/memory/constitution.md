# ev-booking Constitution

## Core Principles

### I. 문서 기반 정책과 결정 추적

작업 시작 전에 `docs/prd.md`, `docs/acceptance.md`, `docs/tasks.md`를 모두 읽고
`AGENTS.md`의 작업 지침을 따른다. 기능의 정책 근거와 범위는 관련 US·AC·T 번호로 추적한다.
작업 목록만으로 PRD와 AC의 정책을 변경하지 않는다.

문서에 없는 금액, 시간 경계, 자격, 상태 전이, 대기 순서, 권한, 실패 처리는 임의로 정하지 않는다.
문서 간 충돌이나 복수 해석은 관련 문서·US·AC·T·C 번호와 함께 사용자에게 확인한다.
조건부 AC와 C 항목은 단순 문서 승인이나 헌법 제정으로 확정되지 않는다.
관련 동작의 테스트 기대값과 구현을 확정하기 전에 사용자 답변을 받고
PRD·AC·작업 목록을 함께 갱신한다. 이는 추측이 제품 정책으로 굳어지는 것을 방지한다.

### II. 학습용 로컬 시연과 데이터 보호

서비스는 학습용 로컬 모바일 웹으로만 실행하고 외부 배포하지 않는다.
실제 충전소 이용·주차면·충전량을 보장하지 않는 가상 예약임을 화면에 안내한다.
충전소 원본 `../ev-map/data`를 임의로 수정하거나 재수집하지 않는다.
예약·결제·환불·대기·시연 계정·운영자 설정은 원본과 별도로 관리한다.

결제와 환불은 토스페이먼츠 테스트 모드만 사용하며 실제 결제를 수행하지 않는다.
인증키·비밀값은 코드, 문서, 로그에 노출하지 않는다.
시연 계정이나 관찰된 충전기 상태를 실제 운영기관의 권한 또는 현장 이용 가능 증거로 표현하지 않는다.
이 제약은 학습용 시연의 결과와 실제 운영 결과를 구분하기 위한 필수 조건이다.

### III. 테스트 우선 (NON-NEGOTIABLE)

**모든 기능은 수용 기준(AC 번호)마다 테스트를 먼저 쓰고, 사용자가 확인하고,
실패하는 것을 확인한 다음에 구현한다. 구현 단계에서는 테스트 파일을 고치지 않는다.**

- 각 AC 번호에 대응하는 실행 가능한 테스트를 구현 전에 작성한다.
  테스트 이름 또는 추적 정보에 AC 번호를 명시하고 GIVEN/WHEN/THEN과 해당 경계 사례를 검증한다.
  하나의 AC를 여러 T 작업이 나누어 구현하면 이번 작업의 검증 부분과 미검증 부분을 구분한다.
- 작성한 테스트 파일, AC 대응 관계, 입력·기대 결과를 사용자에게 제시하고 명시적 확인을 받는다.
  기능 구현 요청이나 문서의 일반 승인을 테스트 확인으로 대신하지 않는다.
- 사용자 확인 후 구현 전에 테스트를 실제 실행하여 대상 기능의 미구현 또는 동작 불일치로
  실패하는 것을 확인한다. 실행 명령, 실패한 AC, 실패 이유와 결과를 기록한다.
  실행하지 않은 테스트, 건너뛴 테스트, 환경·인증 오류만으로 실패한 실행은 이 관문을 충족하지 않는다.
- 사용자 확인과 실패 증거가 모두 있는 경우에만 해당 기능 구현을 시작한다.
  구현과 리팩터링 중에는 승인된 테스트 파일을 변경·삭제하거나 기대값을 완화하지 않는다.
  테스트를 건너뛰거나 실행 설정을 바꾸어 실패를 숨기는 방식으로 통과시키지 않는다.
- 테스트의 오류나 정책 변경이 발견되면 기능 구현을 중단한다.
  원인과 영향 AC를 사용자에게 알리고 필요한 정책 확인을 거친 뒤 별도 테스트 작성 단계로 돌아간다.
  수정된 테스트는 다시 사용자 확인과 실패 확인을 마친 후 구현을 재개한다.

이 절차는 구현에 맞춰 수용 기준을 바꾸는 일을 막는다.
미확정 정책은 임의 기대값으로 테스트하지 않고 관련 C 항목이 해결될 때까지 보류한다.

### IV. 시간·상태·금액·권한의 일관성

정책의 시간 표시와 판정은 서울 시간 `Asia/Seoul`의 시연용 시계를 따른다.
실제 컴퓨터 시간과 토스페이먼츠 외부 테스트 시스템의 시간을 변경하지 않는다.
확정된 시간 경계는 포함·제외를 정확히 지키고 예약 구간은 시작 포함·종료 제외로 처리한다.
기한 동시성·시계 복구 등 미확정 해석은 C 항목의 답변을 받기 전 확정하지 않는다.

임시 점유·결제 대기·대기 신청과 승인 확인 후 확정된 예약을 구분한다.
성공 화면만으로 예약이나 결제를 확정하지 않는다.
같은 충전기의 겹치는 확정 예약·유효 임시 점유, 사용자당 진행 중 예약 2건을 만들지 않는다.
결제·환불·종료·취소·노쇼·승계 요청의 반복 처리로 금액이나 기록을 중복 반영하지 않는다.
사용자 취소·운영자 취소·노쇼를 별도 사유로 기록하고 원래 예약 구간을 보존한다.

운전자는 자신의 예약·대기만, 운영자는 담당 충전소의 관리 기능만 조작할 수 있다.
권한은 화면 표시뿐 아니라 실제 조회·명령 처리 경로에서 검사한다.
운영자 차단 해제로 원본의 예약 제한을 우회하지 않는다.
이 원칙은 화면, 상태 기록, 결제 결과와 권한 판정이 서로 어긋나지 않도록 한다.

### V. 검증 증거와 완료 범위의 정직성

검증은 AC 번호별로 `PASS / FAIL / BLOCKED / NOT_RUN`을 기록한다.
`PASS`는 해당 범위의 검사를 실제 실행하고 기대 결과를 확인한 경우에만 사용한다.
실행했으나 기대와 다르면 `FAIL`, 환경·키·미확정 정책 등으로 진행할 수 없으면 `BLOCKED`,
실행하지 않았으면 `NOT_RUN`으로 기록한다.

정적 확인, 모의 처리, 로컬 모바일 브라우저 검증, 토스 테스트 실연결 결과를 분리한다.
모의 결제의 통과를 토스 실연결 통과로 보고하지 않는다.
부분 구현이나 기반 모듈 검증을 전체 AC 또는 전체 서비스 완료로 확대하지 않는다.
완료 보고에는 변경 파일, 관련 US·AC·T, 실행 방법, 결과와 남은 제한을 기록한다.
시연 지표로 실제 운전자의 헛걸음이나 노쇼 감소 효과를 검증했다고 주장하지 않는다.

## 제품·데이터·결제 제약

- 제품 정책의 상세 근거는 `docs/prd.md` 4.2와 `docs/acceptance.md`이다.
  초안 문서 안에서도 확정 정책과 열린 질문·조건부 기준을 구분한다.
- 충전기는 `statId + chgerId`로 식별한다. 유효한 상태 변경 시각이 더 최신인 변경분만 반영하고
  수집 시각과 상태 갱신 시각을 구분한다. 누락 사양을 만들어 내거나 실시간 정보로 표시하지 않는다.
- 예약 대상은 이용 제한·삭제 없음, 24시간 안내, 유효 상태 `2/3`, 운영자 차단 없음의 조건을 따른다.
  24시간 문자열의 판별 범위와 담당 충전소 선택은 C-05 확정 전 임의로 확대하지 않는다.
- 예약 시작은 현재 이상·현재 + 7일 이하, 매시 00분·30분이며 길이는 30·60·90분이다.
  종료는 7일을 넘어도 된다. 노쇼 승계의 남은 이용시간에는 관련 AC의 예외를 적용한다.
- 예약금은 테스트 금액 3,000원이다. 사용자 취소는 원래 시작까지 120분 이상 3,000원,
  30분 이상·120분 미만 1,500원, 30분 미만·시작 후 0원 환불이다.
  정상 종료·운영자 취소·승인 후 자리 확보 실패는 전액 환불, 노쇼는 0원이다.
- 일반 체크인은 시작 10분 전 포함·시작 15분 후 제외이다.
  미체크인 노쇼를 정상 종료로 바꾸어 환불하지 않는다.
  승계의 조기 체크인·잔여시간 재검사·동시 기한은 관련 C 답변을 따른다.
- 대기는 같은 충전기와 원래 시작·종료가 모두 같은 예약에 연결하고 신청 시각 순서를 따른다.
  사용자당 진행 중 예약 1건과 별도로 대기 1건을 허용하며 대기 신청은 무결제이다.
  운영자 취소는 연결 대기도 취소하고 승계하지 않는다.
- 운전자 테스트 계정 3개, 운영자 테스트 계정 1개와 담당 충전소 1곳을 사용한다.
  결과 알림은 화면 안에서 제공하며 외부 알림·실시간 API 재수집·충전기 원격 제어는 범위 밖이다.
- 기술 구성은 C-10 및 T-01에서 사용자와 합의한 뒤 사용한다.
  제품 정책에 영향을 주지 않는 내부 선택은 합의한 구성 안에서 결정한다.

## 개발 절차와 품질 관문

1. **범위 확인:** 필수 문서와 요청받은 T 작업을 읽고 관련 US·AC·C 및 선행 T의 실제 완료 증거를 확인한다.
   미확정 정책에 의존하는 작업은 답변과 문서 갱신 전 시작하지 않는다.
2. **테스트 작성:** 확정된 관련 AC마다 이번 작업에 필요한 테스트를 먼저 작성한다.
   필요한 추가 작업은 별도로 설명하고 기능 구현을 앞당기지 않는다.
3. **사용자 확인:** 구체적인 테스트 파일과 기대 결과를 사용자에게 제시해 확인받는다.
   답변이 없으면 이 관문 이후의 기능 구현은 진행하지 않는다.
4. **실패 확인:** 승인된 테스트를 실제 실행하여 대상 기능에 대한 실패를 기록한다.
   실행 환경 문제는 해결하거나 `BLOCKED`로 보고하고 구현 착수 근거로 사용하지 않는다.
5. **구현·리팩터링:** 테스트 파일을 고치지 않고 요청받은 T의 범위 안에서 구현한다.
   승인된 테스트를 다시 실행하여 통과를 확인하고 리팩터링 후에도 통과를 유지한다.
6. **완료 검토:** AC별 결과, 테스트 파일 변경 여부, 정책·권한·원본 보호와 실제 변경 범위를 확인한다.
   T-47~T-49의 실연결·브라우저 검증은 실제 수행한 결과만 기록한다.
   통합 검증의 실패 수정은 원인별 작업으로 나누고 전체 서비스를 한 작업에서 다시 구현하지 않는다.

## Governance

이 헌법은 프로젝트의 개발·검증 절차에 적용한다.
제품 정책과 작업 범위는 `AGENTS.md`, PRD, AC, 작업 목록에 근거하며
헌법이나 템플릿을 이유로 확정 정책을 임의로 덮어쓰지 않는다.
문서 충돌은 관련 번호와 영향을 제시하고 사용자 확인으로 해결한다.

헌법 개정은 변경 이유, 영향 원칙, 관련 문서·작업·테스트 및 적용 방안을 제시하고
사용자의 명시적 승인을 받은 뒤 반영한다. 테스트 우선 조항은 NON-NEGOTIABLE이며
일정·편의·단순 구현 요청으로 예외를 만들지 않는다.
헌법 개정만으로 미확정 제품 정책이나 조건부 AC를 확정하지 않는다.

버전은 의미적 버전 관리로 기록한다. 기존 원칙의 제거·호환되지 않는 재정의는 MAJOR,
원칙·절 추가 또는 실질적 확장은 MINOR, 의미를 바꾸지 않는 문구 정리는 PATCH를 증가시킨다.
최초 제정은 1.0.0이며 제정일을 유지하고 실제 개정일을 ISO 날짜로 갱신한다.
개정 시 상단 Sync Impact Report에 버전·원칙·절 변경과 후속 사항을 기록하고
검토 후 커밋 전에 임시 보고서를 제거한다.

각 작업의 착수·완료 검토와 PR 검토에서 헌법 준수 여부를 확인한다.
사용자 테스트 확인, 구현 전 실패 실행, 구현 중 테스트 파일 불변의 증거가 없으면
해당 기능을 이 헌법에 따른 구현 완료로 보고하지 않는다.
종속 템플릿과 명령은 실행 시 이 헌법을 읽으며 헌법 작성 작업에서 함께 변경하지 않는다.
